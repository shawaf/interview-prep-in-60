Minutes 0–5

Big-O: how fast does it grow?

  • Big-O counts how the number of steps grows as the input size n grows. Drop constants: 3n + 5 is O(n).
  • One loop over the input is O(n). A loop inside a loop is O(n²). Halving the search space each step is O(log n). Sorting is O(n log n).
  • Space complexity is the same idea for extra memory (a hash map of n items is O(n) space).
  • The trick most beginners miss: read the constraints first. They tell you which complexity the judge expects.

Minutes 5–12

Arrays & hash maps

  • Array / list: items side by side in memory. Reading a[i] is instant. Searching for a value means checking every item.
  • Hash map (dict) / hash set (set): jump straight to a key. Lookup, insert and delete are O(1) on average.
  • The most common speed-up in all of LeetCode: replace an inner search loop with a hash map lookup. That turns O(n²) into O(n).
  • Use it to answer "have I seen this before?", "how many times?", and "where was it?".

def twoSum(nums, target):
    seen = {}                      # value -> index
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:           # O(1) lookup instead of a second loop
            return [seen[need], i]
        seen[x] = i

Minutes 12–17

Two pointers

  • Two indexes walk through the array, usually one from each end, or both from the left at different speeds.
  • Clue words: sorted array, pair / triplet that sums to a target, palindrome, reverse in place, remove duplicates.
  • Each step moves one pointer, so the whole thing is O(n) with O(1) extra space.
Animation · pair that sums to 14 in a sorted array

def twoSumSorted(a, target):
    l, r = 0, len(a) - 1
    while l < r:
        s = a[l] + a[r]
        if s == target: return [l, r]
        if s < target: l += 1      # need bigger -> move left pointer right
        else: r -= 1               # need smaller -> move right pointer left

Minutes 17–22

Sliding window

  • A window [L..R] over a contiguous subarray or substring. Grow it by moving R; shrink it by moving L when it breaks a rule.
  • Clue words: longest / shortest / max sum subarray or substring, "at most k", "without repeating".
  • Both pointers only move forward, so it's O(n) instead of checking every subarray in O(n²).
Animation · longest substring without repeating characters

def lengthOfLongestSubstring(s):
    window, l, best = set(), 0, 0
    for r, ch in enumerate(s):
        while ch in window:        # rule broken -> shrink from the left
            window.remove(s[l]); l += 1
        window.add(ch)
        best = max(best, r - l + 1)
    return best

Minutes 22–26

Stack (and queue)

  • Stack = last in, first out, like a pile of plates. In Python: a list with append() and pop().
  • Queue = first in, first out, like a line at a shop. In Python: collections.deque with append() and popleft().
  • Clue words for stack: matching brackets, undo, "next greater element", evaluate an expression, nested structures.
Animation · valid parentheses

def isValid(s):
    pairs = {')': '(', ']': '[', '}': '{'}
    stack = []
    for ch in s:
        if ch in pairs:            # closer: must match the top
            if not stack or stack.pop() != pairs[ch]: return False
        else:
            stack.append(ch)       # opener: push
    return not stack

Minutes 26–31

Binary search

  • On sorted data, check the middle and throw away the half that can't contain the answer. 1,000,000 items need only about 20 checks: O(log n).
  • Clue words: sorted, "find the position", "minimum value that works", n up to 10⁹, required O(log n).
  • Advanced use: binary search on the answer ("smallest speed that finishes in time") when you can check one guess quickly.
Animation · find 72

def search(a, target):
    lo, hi = 0, len(a) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if a[mid] == target: return mid
        if a[mid] < target: lo = mid + 1   # answer is on the right
        else: hi = mid - 1                 # answer is on the left
    return -1

Minutes 31–35

Linked list

  • Each node holds a value and a next pointer. No indexes: to reach item k you walk k steps.
  • Almost every problem is pointer juggling. Draw boxes and arrows on paper before coding.
  • Two standard tricks: a dummy head node to avoid edge cases, and fast/slow pointers (slow moves 1, fast moves 2) to find the middle or detect a cycle.
Animation · reverse a linked list

def reverseList(head):
    prev, curr = None, head
    while curr:
        nxt = curr.next     # 1. remember the rest of the list
        curr.next = prev    # 2. flip the arrow
        prev, curr = curr, nxt  # 3. step forward
    return prev

Minutes 35–43

Trees: DFS and BFS

  • A binary tree node has val, left, right. A BST keeps left < node < right, so searching it is like binary search.
  • DFS (depth-first) goes deep first. Write it with recursion: solve for left child, solve for right child, combine. Most tree problems are 5 lines of DFS.
  • BFS (breadth-first) goes level by level with a queue. Use it for "level order", "minimum depth", "right side view".
  • Recursion recipe: (1) base case if not node: return ... (2) trust the call on children (3) combine.
Animation · traversal order 

def maxDepth(root):                       # DFS with recursion
    if not root: return 0
    return 1 + max(maxDepth(root.left), maxDepth(root.right))

from collections import deque
def levelOrder(root):                     # BFS with a queue
    if not root: return []
    q, out = deque([root]), []
    while q:
        level = []
        for _ in range(len(q)):           # everything currently in q = one level
            node = q.popleft(); level.append(node.val)
            if node.left: q.append(node.left)
            if node.right: q.append(node.right)
        out.append(level)
    return out

Minutes 43–49

Graphs and grids

  • A graph is nodes plus edges. Store it as an adjacency list: graph = {node: [neighbours]}.
  • A 2D grid is a graph in disguise: each cell's neighbours are up, down, left, right.
  • Same DFS / BFS as trees, plus one rule: keep a visited set, because graphs can have cycles.
  • BFS finds the shortest path when every edge costs the same. Weighted edges need Dijkstra (learn later).
Animation · number of islands (BFS flood fill)

from collections import deque
def numIslands(grid):
    R, C, seen, count = len(grid), len(grid[0]), set(), 0
    for r in range(R):
        for c in range(C):
            if grid[r][c] == "1" and (r, c) not in seen:
                count += 1
                q = deque([(r, c)]); seen.add((r, c))
                while q:                                  # flood this island
                    y, x = q.popleft()
                    for ny, nx in ((y+1,x),(y-1,x),(y,x+1),(y,x-1)):
                        if 0 <= ny < R and 0 <= nx < C and grid[ny][nx] == "1" and (ny, nx) not in seen:
                            seen.add((ny, nx)); q.append((ny, nx))
    return count

Minutes 49–54

Backtracking

  • Build a solution one choice at a time. After exploring a choice, undo it and try the next one.
  • Clue words: "all combinations", "all permutations", "all subsets", "generate every…", small n (≤ 20).
  • Template: choose → explore (recurse) → un-choose. Cost is exponential, which is fine because n is tiny.
Animation · all subsets of [1, 2, 3]

def subsets(nums):
    res, path = [], []
    def bt(start):
        res.append(path[:])              # every path is a valid subset
        for j in range(start, len(nums)):
            path.append(nums[j])         # choose
            bt(j + 1)                    # explore
            path.pop()                   # un-choose (backtrack)
    bt(0)
    return res

Minutes 54–60

Dynamic programming

  • DP = recursion that remembers answers to sub-problems so each one is solved once.
  • Clue words: "number of ways", "minimum cost", "maximum profit", "can you reach", where each choice depends on smaller versions of the same problem.
  • Recipe: (1) define dp[i] in words (2) write how dp[i] uses smaller i (3) set base cases (4) fill the table in order.
  • Quick start: write the plain recursion, then add @cache from functools. That's top-down DP.
Animation · climbing stairs, 1 or 2 steps at a time, n = 8

def climbStairs(n):                  # bottom-up table
    dp = [1, 1] + [0] * (n - 1)
    for i in range(2, n + 1):
        dp[i] = dp[i-1] + dp[i-2]    # arrived by a 1-step or a 2-step
    return dp[n]

from functools import cache
@cache                               # same thing, top-down
def ways(i):
    return 1 if i <= 1 else ways(i-1) + ways(i-2)

How to attack a problem (in order)

  1. Read the constraints. Use the Big-O table to know the target complexity.
  2. Solve the examples by hand on paper. Notice what your brain does.
  3. Say the brute force out loud, even if it's slow. Note its Big-O.
  4. Find the bottleneck and match it to a pattern: a repeated search becomes a hash map; a nested loop on sorted data becomes two pointers.
  5. Code from the template above, then rename variables to fit.
  6. Test edge cases: empty input, one element, all duplicates, negatives, already sorted.

How to spend 45 minutes

  1. 0–5 · Clarify. Restate the problem. Ask about input size, ranges, duplicates, negatives, empty input, and the output format. Write down one example and one edge case.
  2. 5–12 · Brute force, then improve. Say the naive approach and its Big-O. Name the bottleneck ("the inner loop searches for the complement"). Match it to a pattern ("a hash map makes that lookup O(1)").
  3. 12–15 · Agree on the plan. "I'll use X, giving O(n) time and O(n) space. Sound good?" Only code once the interviewer agrees.
  4. 15–35 · Code while narrating. Use helper functions for clarity. If you're unsure about a detail, say so and leave a # TODO instead of stalling.
  5. 35–42 · Test. Trace your example line by line, then the edge cases. Fix bugs calmly. Finding your own bug is a positive signal.
  6. 42–45 · Wrap up. Restate the complexity, mention possible improvements, and answer follow-ups.

Complexity analysis

Big-O describes how the work grows as the input grows. It ignores the machine and the constants and keeps only the shape of the growth. It is how you know a solution will pass before you run it.

Five rules for counting

  1. Steps in sequence add. A loop over n followed by another loop over n is O(n + n) = O(n).
  2. Nested steps multiply. A loop over n inside a loop over m is O(n · m).
  3. Keep the biggest term and drop constants. O(3n² + 10n + 7) is O(n²). For large n the biggest term dominates everything else.
  4. Different inputs get different letters. Looping over string a and, inside it, string b is O(a · b), not O(n²).
  5. Halving gives a log. If each step cuts the remaining work in half, you need about log₂(n) steps. log₂(1,000,000) ≈ 20, so O(log n) is almost free.

Cost of recursion: count the call tree

Total time = number of calls × work per call. When a function calls itself twice and goes n levels deep, the calls form a tree with about 2ⁿ nodes. The tree below is plain recursive Fibonacci. The yellow nodes are the same call computed again. Remembering those answers is exactly what dynamic programming does.

Diagram · call tree of fib(4)
  • Two branches, depth n: O(2ⁿ). With memoization each distinct call runs once: O(n).
  • Merge sort: depth log n, and each level does O(n) total work: O(n log n).
  • Binary search: one branch, depth log n: O(log n).

Space complexity

  • Count the extra memory you create: a set of n items is O(n), a few variables are O(1).
  • Recursion uses memory. Each pending call sits on the call stack, so DFS on a tree of height h uses O(h). For a tree that's one long chain, h = n.
  • The output you must return is usually not counted.
  • Python's default recursion limit is about 1000 calls. For deeper recursion, use sys.setrecursionlimit or an explicit stack.

Amortized O(1)

A Python list reserves extra capacity. When it fills, it copies everything into a block about twice as big. That copy is O(n), but it happens so rarely that n appends cost O(n) in total, so each append is O(1) amortized (on average across many calls).

One problem, three trade-offs

def has_dup(a):            # O(n²) time, O(1) space: compare every pair
    for i in range(len(a)):
        for j in range(i + 1, len(a)):
            if a[i] == a[j]: return True
    return False

def has_dup(a):            # O(n) time, O(n) space: spend memory to save time
    return len(set(a)) != len(a)

def has_dup(a):            # O(n log n) time, O(1) extra: sort, then compare neighbours
    a.sort()
    return any(a[i] == a[i + 1] for i in range(len(a) - 1))

All three are correct. Choosing between them by time and memory is what interviewers want to hear you discuss.

Arrays & strings

An array stores items in one continuous block of memory. That's why reading any index is instant and inserting in the middle is slow.

How it works

  • The address of item i is start + i × item_size. One multiplication, so a[i] is O(1).
  • Inserting or deleting in the middle forces every later item to shift by one slot: O(n).
  • A Python list is a dynamic array. It grows automatically, and append/pop at the end are O(1).
  • Strings are arrays of characters, but immutable in Python. Every "change" builds a new string.
Animation · inserting 9 at index 2

Technique 1 · Prefix sums

Precompute running totals once in O(n). After that, the sum of any range is one subtraction: sum(a[l..r]) = pre[r+1] − pre[l]. Use it whenever a problem asks for many range sums, or for "subarray sum equals k" together with a hash map.

Animation · build prefix sums, then answer a range query

pre = [0]
for x in nums:
    pre.append(pre[-1] + x)      # pre[i] = sum of nums[0..i-1]

def range_sum(l, r):             # inclusive l..r, O(1)
    return pre[r + 1] - pre[l]

Technique 2 · Kadane's algorithm (maximum subarray)

Walk left to right, keeping the best sum of a subarray that ends here. If the running sum goes negative, it can only hurt what comes next, so start fresh.

def maxSubArray(nums):
    best = cur = nums[0]
    for x in nums[1:]:
        cur = max(x, cur + x)    # extend the old subarray or start a new one at x
        best = max(best, cur)
    return best

def moveZeroes(nums):

Common mistakes

  • Off-by-one errors: is the end index inclusive or exclusive? Decide and write it down.
  • Removing items from a list while looping over it. Build a new list or use a write pointer.
  • Forgetting empty input, a single item, or all-equal items.
  • Building strings with += in a loop (O(n²)).
Habit: if the input isn't sorted and order doesn't matter, ask "would sorting first make this easy?" Sorting costs O(n log n) and unlocks two pointers, binary search and greedy approaches.

Hash maps & sets

A hash map turns a key into an array index with a hash function, so it can jump straight to the data instead of searching for it.

How it works

  1. A hash function turns the key (a word, a number, a tuple) into a big integer.
  2. hash % number_of_buckets picks a bucket, which is just an array slot.
  3. Two keys can land in the same bucket. That's a collision. The bucket keeps a small list (chaining), or the table probes the next free slot (open addressing, which Python's dict uses).
  4. When the table gets too full, it doubles its size and re-inserts everything. That keeps buckets short, so operations stay O(1) on average.

Count subarrays that sum to k, even with negative numbers. If pre[j] − pre[i] = k, then subarray i..j−1 sums to k. So at each position, ask how many earlier prefixes equal current − k.

def subarraySum(nums, k):
    count, cur = 0, 0
    seen = {0: 1}                   # prefix sum -> how many times seen
    for x in nums:
        cur += x
        count += seen.get(cur - k, 0)
        seen[cur] = seen.get(cur, 0) + 1
    return count

Pattern 5 · Smart starting points

def longestConsecutive(nums):

    for x in s:
        if x - 1 not in s:              # x starts a sequence
            y = x
            while y + 1 in s: y += 1
            best = max(best, y - x + 1)
    return best

Two pointers

Use two indexes so that every step safely rules out part of the input. Most nested-loop solutions on sorted data become a single pass.

Why it's correct (the part most tutorials skip)

In sorted Two Sum, if a[l] + a[r] is too small, then a[l] plus any remaining number is also too small, because a[r] is the biggest one left. So a[l] can never be part of the answer, and moving l right loses nothing. The same argument works in reverse for r. Every move throws away a whole row of pairs, which is why n steps are enough to cover all n² pairs.

Shape 1 · Opposite ends, moving inward

For sorted pair sums, palindromes, reversing in place and "container" problems.

def maxArea(height):                  # Container With Most Water
    l, r, best = 0, len(height) - 1, 0
    while l < r:
        best = max(best, (r - l) * min(height[l], height[r]))
        if height[l] < height[r]: l += 1   # the shorter wall limits the area, so move it
        else: r -= 1
    return best

Shape 2 · Same direction (reader and writer)

def removeDuplicates(nums):           # sorted input; keep one of each
    w = 1
    for r in range(1, len(nums)):
        if nums[r] != nums[w - 1]:
            nums[w] = nums[r]; w += 1
    return w

Shape 3 · One pointer in each of two arrays

def merge(a, b):                      # merge two sorted lists
    i = j = 0; out = []
    while i < len(a) and j < len(b):
        if a[i] <= b[j]: out.append(a[i]); i += 1
        else: out.append(b[j]); j += 1
    return out + a[i:] + b[j:]

Shape 4 · Fast and slow

One pointer moves twice as fast. Use it to find the middle of a linked list or to detect a cycle. It's covered in Linked lists.

Worked example · 3Sum

Find all unique triplets that sum to 0. Sort first. Fix the first number, then run sorted Two Sum on the rest. Skip equal values so you don't repeat triplets. Total: O(n²), which beats O(n³).

def threeSum(nums):
    nums.sort(); res = []
    for i in range(len(nums) - 2):
        if i > 0 and nums[i] == nums[i - 1]: continue    # skip duplicate first number
        l, r = i + 1, len(nums) - 1
        while l < r:
            s = nums[i] + nums[l] + nums[r]
            if s < 0: l += 1
            elif s > 0: r -= 1
            else:
                res.append([nums[i], nums[l], nums[r]])
                l += 1
                while l < r and nums[l] == nums[l - 1]: l += 1   # skip duplicate second number
    return res

Common mistakes

  • Using converging pointers on unsorted data. The "safe to discard" argument needs sorted order.
  • l < r vs l <= r. Ask whether one item can pair with itself.
  • A branch that doesn't move either pointer, causing an infinite loop.
  • Duplicate answers in 3Sum or 4Sum because equal values weren't skipped.

Sliding window

Keep a running summary of a contiguous range. Update it when an item enters on the right or leaves on the left, instead of recomputing the whole range.

Fixed-size window (size k)

def findMaxAverage(nums, k):
    s = sum(nums[:k]); best = s
    for r in range(k, len(nums)):
        s += nums[r] - nums[r - k]      # one item enters, one leaves
        best = max(best, s)
    return best / k

Variable-size window: the universal template

l = 0
for r in range(len(a)):
    add(a[r])                   # 1. expand: include a[r]
    while window_is_invalid():  # 2. shrink until valid again
        remove(a[l]); l += 1
    best = max(best, r - l + 1) # 3. record (for "longest")
Longest vs shortest. For the longest valid window, record after shrinking, as above. For the shortest window that satisfies a condition, record inside the while loop: while the window is valid, record it, then shrink.
def minSubArrayLen(target, nums):       # shortest subarray with sum >= target
    l, s, best = 0, 0, float('inf')
    for r, x in enumerate(nums):
        s += x
        while s >= target:              # valid -> record, then try smaller
            best = min(best, r - l + 1)
            s -= nums[l]; l += 1
    return 0 if best == float('inf') else best

Windows that track counts

Longest Repeating Character Replacement: a window is valid when length − count of its most common letter ≤ k, meaning the other letters fit within k replacements.

def characterReplacement(s, k):
    cnt, l, maxf, best = {}, 0, 0, 0
    for r, ch in enumerate(s):
        cnt[ch] = cnt.get(ch, 0) + 1
        maxf = max(maxf, cnt[ch])
        while (r - l + 1) - maxf > k:
            cnt[s[l]] -= 1; l += 1
        best = max(best, r - l + 1)
    return best

Trick · "exactly K" = atMost(K) − atMost(K − 1)

Windows with exactly K distinct values are hard to slide directly, because adding an item can make the window invalid in either direction. Counting windows with at most K is easy. Subtract two of those counts.

When sliding window fails

  • The rule must be monotonic: shrinking a valid window keeps it valid (or growing an invalid one keeps it invalid).
  • With negative numbers, a sum can drop as the window grows, so "sum ≥ target" isn't monotonic. Use prefix sums + hash map instead.
  • For the max or min inside each window, use a monotonic deque (see Stacks & queues).

Stacks, queues & monotonic stacks

A stack gives back the most recent item first. A queue gives back the oldest item first. Choosing the right one sets the order your algorithm processes things in.

The operations

  • Recursion is a stack. Every function call is pushed on the call stack and popped when it returns. Any recursive DFS can be rewritten with an explicit stack.
  • BFS is a queue. Nodes are processed in the order they were discovered.
  • Stacks are good at anything nested or "most recent unmatched": brackets, undo, HTML tags, expression evaluation.

Monotonic stack: "next greater element" in O(n)

Keep the stack in decreasing order. When a bigger value arrives, it is the answer for every smaller value it pops. Each index is pushed once and popped once, so the total is O(n) even though there's a loop inside a loop.

Animation · next greater element with a monotonic stack

def dailyTemperatures(t):              # days until a warmer day
    ans, st = [0] * len(t), []         # st holds indexes, temps decreasing
    for i, x in enumerate(t):
        while st and t[st[-1]] < x:
            j = st.pop()
            ans[j] = i - j             # found the next warmer day for j
        st.append(i)
    return ans

Variations: "next smaller" uses an increasing stack. "Previous greater" reads the top before pushing. "Circular array" loops through the array twice.

Monotonic deque: max of every window

from collections import deque
def maxSlidingWindow(nums, k):
    dq, out = deque(), []              # indexes, values decreasing front to back
    for i, x in enumerate(nums):
        while dq and nums[dq[-1]] < x: dq.pop()  # smaller values can never be the max again
        dq.append(i)
        if dq[0] == i - k: dq.popleft()           # front fell out of the window
        if i >= k - 1: out.append(nums[dq[0]])
    return out

Common mistakes

  • Calling pop() or st[-1] on an empty stack. Always check if st first.

  • Storing values on a monotonic stack when you need distances. Store indexes instead.

Binary search

Binary search works on anything that splits into "no, no, no, yes, yes, yes". Each check halves the region that can still hold the first yes.

The real idea: find the boundary

A sorted array is one example. The general version: you have a condition ok(x) that is false for small x and true for large x. Binary search finds the first true in O(log range) checks. That handles "first position ≥ target", "first bad version", "smallest speed that works" and many more.

Template A · exact match

lo, hi = 0, len(a) - 1
while lo <= hi:                     # the range [lo, hi] is still unchecked
    mid = (lo + hi) // 2
    if a[mid] == x: return mid
    if a[mid] < x: lo = mid + 1
    else: hi = mid - 1
return -1

Template B · first true (lower bound) — learn this one well

def first_true(lo, hi, ok):         # answer is in [lo, hi]; ok is F..F T..T
    while lo < hi:
        mid = (lo + hi) // 2
        if ok(mid): hi = mid        # mid might be the answer, so keep it
        else: lo = mid + 1          # mid is definitely not the answer
    return lo

# first index with a[i] >= x  (same as bisect.bisect_left(a, x))
first_true(0, len(a), lambda i: i == len(a) or a[i] >= x)
No infinite loops: with mid = (lo + hi) // 2, always write lo = mid + 1 and hi = mid. Writing lo = mid can get stuck when hi = lo + 1.

Binary search on the answer

When the question is "what is the minimum X such that…", and checking one X is easy, binary search over the possible values of X.

def minEatingSpeed(piles, h):
    def ok(k):                       # can she finish at speed k?
        return sum((p + k - 1) // k for p in piles) <= h   # ceil(p / k) hours per pile
    lo, hi = 1, max(piles)

        if ok(mid): hi = mid
        else: lo = mid + 1
    return lo

Rotated sorted array

[4,5,6,7,0,1,2]: split at any mid, and at least one half is still sorted. Check whether the target lies inside the sorted half's range. If so, search there; otherwise, search the other half.

def search(a, x):
    lo, hi = 0, len(a) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if a[mid] == x: return mid
        if a[lo] <= a[mid]:                       # left half is sorted
            if a[lo] <= x < a[mid]: hi = mid - 1
            else: lo = mid + 1
        else:                                     # right half is sorted
            if a[mid] < x <= a[hi]: lo = mid + 1
            else: hi = mid - 1
    return -1

Common mistakes

  • Mixing the two templates (using lo <= hi with hi = mid, for example).
  • A search range that doesn't include the answer. For lower bound, hi = len(a), not len(a) − 1.
  • Not checking that the condition really is monotonic.
  • Not using bisect when it already does what you need.

Technique 1 · Dummy head

When the head itself might change (it gets deleted, or you're building a new list), start from a fake node in front of it. Then the head needs no special case. Return dummy.next.

Trees & binary search trees

A tree is a recursive structure: each node is a smaller tree's root. So most tree solutions are "solve it for the children, then combine".

Vocabulary

  • Root = top node. Leaf = no children. Depth of a node = edges from the root. Height of a tree = longest root-to-leaf path.
  • Balanced: height is about log n, so operations are fast. Skewed: basically a linked list, height n.
  • Complete: every level full except possibly the last, filled left to right. Heaps are stored this way.
  • BST: every value in the left subtree < node < every value in the right subtree. That's the whole subtree, not just the direct children.

The three depth-first orders

Animation · traversal orders 

def dfs(node):
    if not node: return
    # pre-order: work here (top-down, e.g. copy/serialize a tree)
    dfs(node.left)
    # in-order: work here (on a BST this visits values in sorted order)
    dfs(node.right)
    # post-order: work here (children are done, e.g. heights, deleting)

Two recursion styles

Bottom-up (return information up). Each call returns something about its subtree, and the parent combines the results. Heights, sizes, "is it balanced", diameter.

def diameterOfBinaryTree(root):
    best = 0
    def height(n):
        nonlocal best
        if not n: return 0
        l, r = height(n.left), height(n.right)
        best = max(best, l + r)      # longest path that bends at n
        return 1 + max(l, r)         # tell the parent my height
    height(root)
    return best

Top-down (pass information down). Each call receives what it needs from its ancestors as parameters. Path sums, allowed value ranges, current depth.

def isValidBST(root):
    def ok(n, low, high):            # every value here must be in (low, high)
        if not n: return True
        if not (low < n.val < high): return False
        return ok(n.left, low, n.val) and ok(n.right, n.val, high)
    return ok(root, float('-inf'), float('inf'))

BST operations

  • Search, insert, delete: go left if smaller, right if bigger. O(h), which is O(log n) if balanced and O(n) if skewed.
  • In-order traversal gives sorted order, so the "kth smallest" is the kth node visited in-order.
  • Lowest common ancestor in a BST: walk down from the root. The first node whose value lies between p and q is the answer.
def kthSmallest(root, k):            # iterative in-order with a stack
    st, n = [], root
    while st or n:
        while n: st.append(n); n = n.left   # go as far left as possible
        n = st.pop(); k -= 1
        if k == 0: return n.val
        n = n.right

Common mistakes

  • Validating a BST by comparing only parent and children. The range must hold for the whole subtree.
  • Forgetting the if not node base case.
  • Mixing up depth (counted from the top) and height (counted from the bottom).
  • Recursion depth on a skewed tree with 10⁵ nodes. Use an iterative version or raise the limit.

Heaps (priority queues)

A heap always hands you the smallest (or largest) item in O(log n), without keeping everything fully sorted.

How it works

  • A complete binary tree stored in a plain array. For index i: parent = (i − 1) // 2, children = 2i + 1 and 2i + 2.
  • Min-heap rule: every parent ≤ its children, so the minimum is always at index 0.
  • Push: add at the end, then sift up (swap with the parent while smaller). Pop: take index 0, move the last item to the top, then sift down (swap with the smaller child). Both are O(log n).

Topological sort: order tasks with prerequisites

Kahn's algorithm: repeatedly take a node with no remaining prerequisites (in-degree 0), output it, and remove its outgoing edges. If some nodes are never output, the graph has a cycle, so no valid order exists. That's exactly the Course Schedule problem.

Animation · Kahn's topological sort (number under each node = in-degree)

def topoSort(n, edges):                  # edge (a, b) means a must come before b
    graph, indeg = defaultdict(list), [0] * n
    for a, b in edges:
        graph[a].append(b); indeg[b] += 1
    q = deque(i for i in range(n) if indeg[i] == 0)
    order = []
    while q:
        u = q.popleft(); order.append(u)
        for v in graph[u]:
            indeg[v] -= 1
            if indeg[v] == 0: q.append(v)
    return order if len(order) == n else []   # [] means there's a cycle

Union-Find (disjoint set): "are these connected?"

Keeps groups of nodes and merges them quickly. With path compression, each operation is almost O(1). Use it for counting components, finding the edge that creates a cycle, or connectivity that changes as edges are added.

parent = list(range(n))
def find(x):
    while parent[x] != x:
        parent[x] = parent[parent[x]]    # path compression: point closer to the root
        x = parent[x]
    return x
def union(a, b):
    ra, rb = find(a), find(b)
    if ra == rb: return False            # already connected, so this edge makes a cycle
    parent[ra] = rb
    return True

import heapq
def dijkstra(src):                       # graph[u] = [(v, w), ...]
    dist = {src: 0}

        d, u = heapq.heappop(h)

Backtracking

Backtracking is DFS over a tree of decisions. Make a choice, explore everything that follows from it, undo it, then try the next choice.

The decision tree

For subsets, each level decides about one number: take it or skip it. The leaves are all 2ⁿ answers. Backtracking walks this tree depth-first and keeps only the current path in memory.

Diagram · take / skip decisions for [1, 2, 3]

The universal template

def backtrack(path, choices):
    if is_complete(path):
        res.append(path[:])          # COPY: path keeps changing after this
        return
    for c in choices:
        if not valid(c, path): continue   # pruning: skip dead branches early
        path.append(c)               # choose
        backtrack(path, next_choices)  # explore
        path.pop()                   # un-choose

def permute(nums):
    res, path, used = [], [], [False] * len(nums)
    def bt():
        if len(path) == len(nums): res.append(path[:]); return
        for i, x in enumerate(nums):
            if used[i]: continue
            used[i] = True; path.append(x)
            bt()
            used[i] = False; path.pop()
    bt(); return res

def combinationSum(cands, target):
    res = []
    def bt(start, path, total):
        if total == target: res.append(path[:]); return
        for j in range(start, len(cands)):
            if total + cands[j] > target: continue   # prune
            path.append(cands[j])
            bt(j, path, total + cands[j])            # j, not j+1: reuse allowed
            path.pop()
    bt(0, [], 0); return res

Handling duplicate inputs

With input like [1, 2, 2], sort first. Then at each level skip a value equal to the previous one: if j > start and nums[j] == nums[j-1]: continue. Equal values are then only picked in order, so the same subset can't be built twice.

Backtracking on a grid (Word Search)

def exist(board, word):
    R, C = len(board), len(board[0])
    def dfs(r, c, i):
        if i == len(word): return True
        if not (0 <= r < R and 0 <= c < C) or board[r][c] != word[i]: return False
        tmp, board[r][c] = board[r][c], '#'          # mark as used (choose)
        found = any(dfs(r+dr, c+dc, i+1) for dr, dc in ((1,0),(-1,0),(0,1),(0,-1)))
        board[r][c] = tmp                            # restore (un-choose)
        return found
    return any(dfs(r, c, 0) for r in range(R) for c in range(C))

Common mistakes

  • res.append(path) instead of path[:]. Every result ends up as the same (empty) list.
  • Forgetting to undo (pop, unmark, restore).
  • No pruning, so the search explores branches that can't work.

Dynamic programming

DP solves a problem from answers to smaller versions of the same problem, and stores each answer so it's computed only once.

When is it DP?

  • Overlapping subproblems: plain recursion solves the same subproblem again and again (see the fib(4) tree in Complexity).
  • Optimal substructure: the best answer is built from best answers to smaller parts.
  • Wording: "number of ways", "minimum / maximum", "is it possible", "longest", over sequences, grids or amounts.

The 5-step recipe

  1. State: define dp[i] (or dp[i][j]) in one English sentence. This is the hardest and most important step.
  2. Transition: how does dp[i] follow from smaller states? Think about the last choice made.
  3. Base cases: the smallest states you know directly.
  4. Order: fill states so everything a state needs is already computed.
  5. Answer: which cell holds it (dp[n], max(dp), the bottom-right…).

def rob(nums):                       # bottom-up with O(1) space
    prev2 = prev1 = 0                # best up to i-2, best up to i-1
    for x in nums:
        prev2, prev1 = prev1, max(prev1, prev2 + x)
    return prev1

1D DP · Coin Change

def coinChange(coins, amount):
    dp = [0] + [float('inf')] * amount      # dp[a] = fewest coins to make a
    for a in range(1, amount + 1):
        for c in coins:
            if c <= a:
                dp[a] = min(dp[a], dp[a - c] + 1)   # last coin used was c
    return dp[amount] if dp[amount] != float('inf') else -1

2D DP · Longest Common Subsequence

dp[i][j] = LCS of the first i letters of one string and the first j letters of the other. If the letters match, extend the diagonal. Otherwise, take the better of dropping a letter from either string.

Animation · LCS of "abcde" and "ace"

def longestCommonSubsequence(a, b):
    dp = [[0] * (len(b) + 1) for _ in range(len(a) + 1)]
    for i in range(1, len(a) + 1):
        for j in range(1, len(b) + 1):
            if a[i-1] == b[j-1]: dp[i][j] = dp[i-1][j-1] + 1
            else: dp[i][j] = max(dp[i-1][j], dp[i][j-1])
    return dp[-1][-1]

0/1 knapsack · Partition Equal Subset Sum

Each item can be used at most once. Loop the capacity backwards so an item isn't counted twice in the same pass.

def canPartition(nums):
    total = sum(nums)
    if total % 2: return False
    target = total // 2
    dp = [True] + [False] * target           # dp[s] = can some items sum to s?
    for x in nums:
        for s in range(target, x - 1, -1):   # backwards!
            dp[s] = dp[s] or dp[s - x]
    return dp[target]

Common mistakes

  • A vague state. If you can't say what dp[i] means in one sentence, stop and define it.
  • Wrong base case (dp[0] for "empty" is often 1 for counting problems and 0 for sums).
  • Filling in the wrong order, or looping forwards in 0/1 knapsack.
  • Returning infinity instead of the −1 the problem asks for.

def mergeSort(a):
    if len(a) <= 1: return a
    mid = len(a) // 2
    L, R = mergeSort(a[:mid]), mergeSort(a[mid:])
    out, i, j = [], 0, 0
    while i < len(L) and j < len(R):
        if L[i] <= R[j]: out.append(L[i]); i += 1
        else: out.append(R[j]); j += 1
    return out + L[i:] + R[j:]

Greedy

A greedy algorithm makes the choice that looks best right now and never revisits it. It's fast and short, but correct only when you can argue that a locally best choice never blocks the overall best answer. If you can't argue it, try DP.

def canJump(nums):                   # Jump Game
    far = 0                          # farthest index reachable so far
    for i, x in enumerate(nums):
        if i > far: return False     # stuck before reaching i
        far = max(far, i + x)
    return True

Intervals

  • Two intervals [a, b] and [c, d] overlap when a <= d and c <= b.
  • Merge overlapping intervals: sort by start, then extend the last merged interval or start a new one.
  • Keep as many non-overlapping intervals as possible: sort by end and greedily keep the one that finishes first. It leaves the most room for the rest.
  • Most overlapping at once (meeting rooms): sort start and end times separately and sweep, or use a min-heap of end times.
def merge(intervals):
    intervals.sort(key=lambda x: x[0])
    out = [intervals[0]]
    for s, e in intervals[1:]:
        if s <= out[-1][1]: out[-1][1] = max(out[-1][1], e)   # overlap, so extend
        else: out.append([s, e])
    return out

Tries & bit manipulation

Two smaller topics that show up regularly: a tree for prefix lookups, and tricks with the binary form of numbers.

Trie (prefix tree)

Each edge is a letter. Words that share a prefix share the same path. A flag marks nodes where a word ends. Insert and search cost O(length of word), no matter how many words are stored.

Diagram · trie holding "cat", "car", "dog" (green ring = end of a word)
class Trie:
    def __init__(self):
        self.root = {}
    def insert(self, word):
        node = self.root
        for ch in word:
            node = node.setdefault(ch, {})   # walk, creating children as needed
        node['$'] = True                     # end-of-word marker
    def _walk(self, s):
        node = self.root
        for ch in s:
            if ch not in node: return None
            node = node[ch]
        return node
    def search(self, word):
        node = self._walk(word); return bool(node) and '$' in node
    def startsWith(self, prefix):
        return self._walk(prefix) is not None

Use a trie for autocomplete, "does any word start with…", and searching many words in a grid at once (Word Search II).

Minutes 0–5

How code actually runs

  • The CPU only understands very simple instructions. Your code gets turned into them either ahead of time by a compiler (C, Go, Rust) or while running by an interpreter or virtual machine (Python, JavaScript, Java's JVM).
  • Memory has two main areas. The stack holds function calls and their local variables, and is freed automatically when a function returns. The heap holds objects that must outlive a single call, and a garbage collector cleans it up in Python, Java and JS.
  • A process is a running program with its own memory. A thread is a worker inside a process, sharing that memory.
  • Speed ladder: CPU cache ≈ 1 ns, RAM ≈ 100 ns, SSD ≈ 100 µs, network round trip ≈ 1–150 ms. Most performance work is about avoiding the slow steps.

Minutes 15–21

Object-oriented design & SOLID

  • A class is a blueprint. An object is one instance of it, with its own data (attributes) and behaviour (methods).
  • Four pillars: encapsulation (hide internal data behind methods), abstraction (show what it does, hide how), inheritance (reuse and extend a parent class), polymorphism (the same call behaves correctly for each type).
  • Prefer composition ("a car has an engine") over deep inheritance ("a car is a vehicle is a machine…").
  • SOLID: Single responsibility · Open for extension, closed for modification · Liskov substitution (a subclass must work wherever its parent does) · Interface segregation (small, focused interfaces) · Dependency inversion (depend on abstractions).
Animation · polymorphism: one loop, three behaviours

from abc import ABC, abstractmethod
import math

class Shape(ABC):
    @abstractmethod
    def area(self) -> float: ...

class Circle(Shape):
    def __init__(self, r): self.r = r

class Square(Shape):

    def area(self): return self.s ** 2

class Triangle(Shape):

Minutes 26–31

How the web works

  • A client (browser or app) sends a request, and a server sends back a response. They speak HTTP, which is structured text.
  • The journey: DNS turns a name into an IP address → a TCP + TLS connection is opened (the S in HTTPS = encrypted) → the HTTP request is sent → server code and database do the work → the response comes back → the browser draws the page.
  • Request = method + path + headers + optional body. Response = status code + headers + body.
  • Status codes: 2xx success · 3xx redirect · 4xx the client did something wrong · 5xx the server broke.
  • HTTP is stateless: every request stands alone. Cookies or tokens carry "who you are" from one request to the next.

Databases & SQL

  • A relational database stores data in tables (rows and columns). A primary key identifies each row. A foreign key points to a row in another table.

Minutes 42–47

Concurrency

  • Concurrency = several tasks in progress, taking turns. Parallelism = tasks running at literally the same moment on different CPU cores.
  • Threads share memory, which is fast but lets them corrupt shared data. Processes have separate memory, which is safer but heavier.
  • Race condition: the result depends on timing. count += 1 is really three steps (read, add, write), and two threads can interleave them.
  • Fix it with a lock (mutex) so only one thread runs the critical section at a time. Taking several locks in different orders can cause a deadlock.
  • Waiting on network or disk (I/O-bound)? Use threads or async. Heavy computation (CPU-bound)? Use multiple processes (in Python, because of the GIL).

System design basics

  • Start simple: one server and one database. Scale only when measurements say you must.
  • Vertical scaling = a bigger machine (easy, but has a ceiling). Horizontal scaling = more machines behind a load balancer (needs stateless servers).
  • Cache hot data in memory (Redis) to skip slow database work. A CDN serves static files from servers near the user.
  • Database scaling: read replicas for heavy reads, sharding (splitting data across machines) for huge datasets.
  • Queues (RabbitMQ, Kafka, SQS) move slow work to background workers and absorb traffic spikes.
  • Every choice is a trade-off: speed vs cost, consistency vs availability, simplicity vs flexibility.

Minutes 53–57

Security essentials

  • Never trust user input. Validate it, and never paste it directly into SQL, HTML or shell commands.
  • SQL injection → use parameterized queries. Cross-site scripting (XSS) → escape anything you put into a page.
  • Store passwords only as slow, salted hashes (bcrypt or argon2). Never plain text, never reversible encryption.
  • Use HTTPS everywhere. Keep secrets (API keys, DB passwords) in environment variables or a secret manager, never in Git.
  • Authentication = who you are. Authorization = what you're allowed to do. Give every user and service the least access it needs.

Object-oriented design round: the approach

  1. Clarify scope: which features, which actors, which constraints? ("Multiple floors? Spot sizes? Payment?")
  2. Find the nouns (candidate classes) and verbs (methods) in the requirements.
  3. Assign responsibilities so each class has one reason to change. Draw the relationships (has-a, is-a).

    @abstractmethod

Python names are references

A variable in Python is a name tag attached to an object, not a box that holds a value. Two names can point at the same object, and changing a mutable object through one name is visible through the other.

Garbage collection

  • Python counts references to each object and frees it when the count hits zero. A separate cycle collector handles objects that point at each other.
  • Java, JavaScript, Go, C# use tracing collectors: they periodically find everything still reachable and free the rest.
  • C/C++: you free memory yourself. Rust: the compiler proves when memory can be freed (ownership).

Git in depth

Git becomes easy once you see it as a graph of snapshots with movable labels on it. Every command either adds nodes to the graph or moves labels.

The mental model

  • Commit = a full snapshot of the project + author + message + a pointer to its parent(s). Its ID is a hash of all that, such as a1b2c3d.
  • Branch = a label pointing at one commit. Committing moves the current branch's label forward.
  • HEAD = "you are here", usually pointing at a branch.
  • Remote (origin) = another copy of the repo, such as on GitHub. origin/main is your last-known position of its main branch.

Merge vs rebase

Both bring the work of two branches together. Merge keeps the true history and adds a merge commit. Rebase replays your commits on top of the latest main, giving a straight line of history, but it creates new commits (new IDs).

Animation · same starting point, two strategies

Golden rule of rebasing: never rebase commits that other people have already pulled. Their copies would still have the old commits, and the histories split.

Clean code & refactoring

Clean code is code that's cheap to change. Every rule below is a way to reduce the time the next reader needs to understand it safely.

Functions

  • Do one thing at one level of detail. If you need "and" to describe it, split it.
  • Keep them short enough to see on one screen. Extract well-named helpers.
  • Few parameters. Group related ones into an object, and avoid boolean "mode" flags: render(page, True) → render_preview(page).
  • Either change something or return something, not both in surprising ways (command-query separation).

Guard clauses remove nesting: handle the special cases first and return early.

# before: the main logic is buried 3 levels deep
def ship(order):
    if order:
        if order.paid:
            if order.items:
                return create_shipment(order)
    return None

# after: exits first, main path at the left margin
def ship(order):
    if not order or not order.paid or not order.items:
        return None
    return create_shipment(order)

Comments

  • Explain why (a business rule, a workaround, a non-obvious decision). If a comment explains what, rename things until it isn't needed.
  • Docstrings for public functions and modules: what it does, the inputs, the output, the errors it raises.
  • Delete commented-out code. Git remembers it.

Principles

  • DRY: one source of truth for each piece of knowledge. Rule of three: duplicate once, and abstract on the third copy, so you don't abstract too early.
  • KISS: the simplest solution that works. Clever code costs more to read than it saves.
  • YAGNI: don't build for imagined future needs.
  • Separation of concerns: keep I/O (files, network, DB) apart from logic. Pure logic is easy to test.
  • Least surprise: a function should do what its name suggests and nothing more.

Composition over inheritance

Inheritance locks in an "is-a" tree early. When behaviours mix (a duck that flies, a robot duck that doesn't, a rubber duck that squeaks), the tree explodes. Composition gives an object parts it can swap.

class Duck:
    def __init__(self, flyer, sound):
        self.flyer, self.sound = flyer, sound    # has-a, swappable
    def fly(self): return self.flyer.fly()
    def speak(self): return self.sound.make()

mallard = Duck(WingFlyer(), Quack())
toy     = Duck(NoFly(), Squeak())

TCP vs UDP: TCP guarantees order and delivery (web pages, APIs, files). UDP accepts loss for speed (video calls, games, DNS queries). HTTP/3 runs on QUIC, which is built on UDP.

DNS: names to addresses

  1. The browser and OS check their caches.
  2. Otherwise they ask a resolver (your ISP, or 1.1.1.1 / 8.8.8.8).
  3. The resolver asks a root server → the .com server → the domain's authoritative server, which has the answer.
  4. The answer is cached for its TTL (time to live).

HTTPS / TLS

TLS gives three guarantees: encryption (nobody can read it), integrity (nobody can change it), and identity (the server's certificate is signed by a trusted authority, so you really are talking to your bank).

State on a stateless protocol

Indexes

  • Usually a B-tree: a sorted, wide, shallow tree. Finding a row among millions takes 3–4 page reads.
  • Index the columns you filter, join and sort on (WHERE, JOIN ... ON, ORDER BY). Primary keys are indexed automatically.
  • Composite index (city, created_at) helps queries filtering by city, or by city and date, but not by date alone (the leftmost-prefix rule).
  • Every index slows down writes and takes space. Don't index everything.
  • Prefix a query with EXPLAIN to see whether it uses an index or scans the whole table.

Normalization in plain words

  • Store each fact once. A customer's address lives in customers, not copied into every order.

Concurrency in depth

Concurrency bugs are rare, timing-dependent, and hard to reproduce. The defense is design: share less, and protect what you must share.

Vocabulary

  • Critical section: code that touches shared data and must not be interleaved.
  • Atomic: happens as one indivisible step. count += 1 is not atomic.
  • Thread-safe: correct even when called from many threads at once.
  • Blocking: a call that waits (reading a file, a network request, acquiring a lock).

Deadlock

Animation · two threads, two locks, wrong order

A deadlock needs all four Coffman conditions: mutual exclusion, hold-and-wait, no preemption, and circular wait. Break any one to prevent it. In practice: always acquire locks in the same global order, hold them briefly, and use timeouts.

  • Starvation: a thread never gets its turn because others keep winning.
  • Livelock: threads keep reacting to each other and never progress (two people stepping aside in a hallway forever).

Python: pick the right model

CPython has a GIL (global interpreter lock), so only one thread runs Python bytecode at a time. Threads still help while waiting on I/O, because waiting releases the GIL. For CPU-heavy work, use processes. (Python 3.13+ has an experimental build without the GIL.)

System design means choosing building blocks and trade-offs so a product stays fast, available and affordable as it grows.

A framework for any design question

  2. Estimates: requests per second, data size per year, read/write ratio.

  4. Data model: tables or documents, and which database fits.

Load balancing

A load balancer spreads requests across servers, removes unhealthy ones (health checks), and lets you add servers without clients noticing. The strategy matters when requests have very different costs.

Animation · 6 requests of different cost, 3 servers

Caching

StrategyHowTrade-off
Cache-asideApp checks the cache, loads from DB on a miss, stores the resultSimple; first request is slow; can serve stale data
Write-throughWrite to cache and DB togetherAlways fresh; slower writes
Write-backWrite to cache, flush to DB laterVery fast writes; risk of loss on a crash
  • Eviction: LRU (least recently used), LFU (least frequently used), or TTL (expire after a set time).
  • Invalidation is the hard part: when data changes, delete or update the cached copy. Short TTLs limit how stale data can get.
  • Layers: browser cache → CDN → application cache (Redis) → database buffer cache.

Scaling the database

  • Indexes and query fixes first. They're the cheapest wins.
  • Read replicas: copies that serve reads. Writes go to the primary. Replicas can lag slightly (eventual consistency).
  • Sharding: split rows across databases by a key (user_id % N, or consistent hashing). Scales writes, but cross-shard queries and joins get hard.
  • Connection pooling: reuse DB connections instead of opening one per request.

Asynchronous processing

Put slow or unreliable work (emails, video encoding, reports) on a queue, and let workers process it. The user gets a fast response, and spikes are smoothed out. Consumers must be idempotent, because messages can be delivered more than once. Pub/sub sends one event to many independent subscribers.

Consistency and CAP

When the network splits a distributed system into parts that can't talk (a partition), each part must choose: keep answering with possibly stale data (availability), or refuse until it can be sure (consistency). Banking leans consistent. A social feed leans available.

Reliability patterns

  • Redundancy: no single point of failure (2+ servers, replicas, multiple zones).
  • Timeouts + retries with exponential backoff and jitter (wait 1s, 2s, 4s… plus randomness so clients don't retry in sync).
  • Circuit breaker: stop calling a failing dependency for a while instead of piling on.
  • Rate limiting protects you from abuse and runaway clients.
  • Graceful degradation: if recommendations are down, show the page without them.

Most breaches don't involve clever cryptography. They exploit ordinary mistakes: trusting input, weak access checks, leaked secrets and outdated dependencies.

Access control: the #1 risk

@app.get("/invoices/{invoice_id}")

Hiding a button in the UI is not security. Anyone can send the request directly. Every check must happen on the server.

XSS and CSRF

  • XSS (cross-site scripting): an attacker stores <script>steal(document.cookie)</script> as their username, and it runs in other users' browsers. Defense: frameworks escape output by default (don't bypass it with innerHTML or |safe), use HttpOnly cookies, and add a Content-Security-Policy header.
  • CSRF (cross-site request forgery): a malicious site makes your browser send a request to your bank with your cookies. Defense: SameSite cookies and CSRF tokens on forms.

Passwords: hashing, not encryption

  • Encryption is reversible with a key. Hashing is one-way. For passwords you never need the original, so hash them.
  • A salt (random value per user) means equal passwords get different hashes, which defeats precomputed tables.
  • Use deliberately slow hashes (bcrypt, argon2, scrypt). Fast hashes like SHA-256 let attackers guess billions per second.
  • Better still: offer MFA, and let users sign in with passkeys or OAuth providers.

Why distributed systems are hard

  • We spread work across machines for scale (one machine isn't enough), availability (survive a machine dying) and latency (be close to users).
  • The cost is partial failure. Some parts work while others don't, and you often can't tell which. A request that times out may have succeeded, failed, or still be running.
  • The fallacies of distributed computing: it's tempting to assume the network is reliable, latency is zero, bandwidth is infinite, and the topology never changes. None of those are true.
  • The basic toolkit: timeouts, retries with backoff, and idempotency so that retrying is safe.

Minutes 4–9

Time & ordering

  • Every machine's clock drifts. Even with NTP syncing, clocks differ by milliseconds, and sometimes jump backwards.
  • So "which happened first?" can't be answered by comparing timestamps from different machines. "Last write wins" by wall clock can silently drop a newer write.
  • Logical clocks track cause and effect instead of real time. A Lamport clock is a counter: increment it on every event, send it with every message, and on receiving, jump to max(mine, theirs) + 1.
  • If A caused B, then L(A) < L(B). Vector clocks go further and can also tell when two events are concurrent.
Animation · Lamport clocks across three processes

class LamportClock:
    def __init__(self):
        self.t = 0
    def tick(self):                 # local event, or just before sending
        self.t += 1
        return self.t
    def receive(self, msg_t):       # message arrived stamped with msg_t
        self.t = max(self.t, msg_t) + 1
        return self.t

Minutes 9–15

Replication

  • Replication = keeping copies of the same data on several machines, for availability, read scaling and geographic closeness.
  • Single-leader (most common): all writes go to the leader, and followers copy its log. Used by PostgreSQL, MySQL, MongoDB replica sets and Redis.
  • Synchronous replication waits for followers before confirming a write (safe, slower). Asynchronous doesn't wait (fast, but recent writes can be lost if the leader dies).
  • Async followers lag behind, so reads can return stale data. That's eventual consistency. The classic fix for users: read-your-own-writes.
  • Other models: multi-leader (writes in several regions, conflicts to resolve) and leaderless with quorums (Cassandra, DynamoDB).

Partitioning (sharding) & consistent hashing

  • When data or write traffic is too big for one machine, split it. Each partition (shard) holds a subset of keys, usually also replicated.
  • Range partitioning (A–F, G–M…) keeps range scans fast but can create hot spots. Hash partitioning spreads load evenly.
  • Naive hash(key) % N breaks when N changes: almost every key moves. Consistent hashing puts nodes and keys on a ring. Each key belongs to the next node clockwise, so adding a node moves only about 1/N of the keys.
  • Used by Cassandra, DynamoDB, Riak, Redis Cluster (hash slots), CDNs and load balancers. Vitess and Citus shard MySQL and PostgreSQL.
Animation · consistent hashing ring

import bisect, hashlib

class Ring:
    def __init__(self, nodes, vnodes=100):          # virtual nodes even out the load
        self.ring = sorted((self._h(f"{n}#{i}"), n) for n in nodes for i in range(vnodes))
        self.points = [h for h, _ in self.ring]
    def _h(self, s):
        return int(hashlib.md5(s.encode()).hexdigest(), 16)
    def node_for(self, key):
        i = bisect.bisect(self.points, self._h(key)) % len(self.ring)  # next point clockwise
        return self.ring[i][1]

Minutes 20–25

CAP & consistency

  • CAP: when a network partition splits your replicas, you must choose between Consistency (every read sees the latest write, or an error) and Availability (every request gets an answer, possibly stale).
  • CP systems refuse requests on the minority side: etcd, ZooKeeper, HBase, Spanner, CockroachDB.
  • AP systems keep answering and reconcile later: Cassandra, DynamoDB (by default), Riak, CouchDB, DNS.
  • PACELC adds the everyday case: even without a partition, you trade latency vs consistency.
  • Quorums: with N replicas, if writes wait for W acks and reads ask R replicas, then R + W > N means every read overlaps the latest write.

Consensus: getting machines to agree

  • Consensus lets a group of machines agree on one value or one order of operations, even when some of them crash. It's the base layer for leader election, distributed locks and configuration.
  • Raft (the readable one) and Paxos (the classic) need a majority. 5 nodes tolerate 2 failures, and 3 nodes tolerate 1. Always use an odd number.
  • Raft in one breath: one leader per term sends heartbeats. If followers stop hearing them, one times out, becomes a candidate and asks for votes. A majority makes it the new leader. The leader replicates a log, and an entry is committed once a majority has stored it.
  • You rarely implement this yourself. You use etcd (Kubernetes' brain), ZooKeeper (Kafka's former coordinator, Hadoop) or Consul. Kafka now has its own Raft (KRaft).

Messaging & event streaming

  • Services talk asynchronously through a broker, so the sender doesn't wait and doesn't need the receiver to be up.
  • Queue (RabbitMQ, Amazon SQS): each message goes to one worker and is deleted once handled. Good for jobs.
  • Log / stream (Apache Kafka, Kinesis, Pulsar, Redpanda): an append-only, retained log. Many independent consumer groups read it at their own pace and can replay it.
  • Kafka: a topic is split into partitions. Messages with the same key go to the same partition, so they stay in order. Within a group, each partition is read by exactly one consumer.
  • Delivery is usually at-least-once: consumers must be idempotent. "Exactly once" in practice means at-least-once plus deduplication.

Minutes 36–41

Transactions across services

  • Inside one database, a transaction is all-or-nothing. Across several services, each with its own database, there's no single COMMIT.
  • Two-phase commit (2PC): a coordinator asks everyone to prepare, then tells everyone to commit. It's correct, but it blocks if the coordinator dies, and it couples services tightly. It's used inside databases, rarely between microservices.
  • Saga: a chain of local transactions. If a step fails, run compensating actions for the steps already done (refund, release stock). Data is eventually consistent.
  • Orchestration (a central coordinator, such as Temporal or AWS Step Functions) vs choreography (each service reacts to events).
  • Outbox pattern: write the business change and the event to publish in the same local transaction, then relay the event to Kafka. You never update the DB but lose the event.

def place_order(order):                      # saga orchestrator
    steps = [(create_order, cancel_order), (charge_payment, refund_payment),
             (reserve_stock, release_stock), (schedule_shipping, cancel_shipping)]
    undo = []
    for action, compensate in steps:
        try:
            action(order)
            undo.append(compensate)
        except Exception:
            for comp in reversed(undo):      # roll back what already happened
                comp(order)
            raise

Minutes 41–46

Microservices & resilience

  • Microservices talk over the network: REST, gRPC (fast, typed), or events. An API gateway (Kong, NGINX, AWS API Gateway) is the single front door.
  • Service discovery (Kubernetes DNS, Consul) finds where instances live. A service mesh (Istio, Linkerd) adds a sidecar proxy (Envoy) to each instance that handles retries, encryption (mTLS) and metrics.
  • One slow dependency can freeze everything as callers pile up waiting: a cascading failure. Defenses: timeouts, retries with jitter, circuit breakers, bulkheads (separate resource pools), rate limiting, and fallbacks.
  • A circuit breaker counts failures. After too many, it "opens" and fails fast, without calling the sick service. After a cool-down it lets one trial request through.
Animation · circuit breaker states

class CircuitBreaker:
    def __init__(self, threshold=3, cooldown=30):
        self.failures, self.threshold, self.cooldown = 0, threshold, cooldown
        self.opened_at = None

    def call(self, fn, *args, fallback=None):
        if self.opened_at and time.time() - self.opened_at < self.cooldown:
            return fallback                         # OPEN: fail fast
        try:
            result = fn(*args)                      # CLOSED, or the HALF-OPEN trial
        except Exception:
            self.failures += 1
            if self.failures >= self.threshold:
                self.opened_at = time.time()        # trip to OPEN
            return fallback
        self.failures, self.opened_at = 0, None     # success: CLOSED again
        return result

System design interview playbook

A system design round is a 45-minute conversation with no single right answer. You're scored on driving it in a structured way, using real numbers, and making and defending trade-offs.

What's expected at each level

LevelExpectation
Junior / new gradOften no system design round, or a light one: a working high-level design, basic components, and sensible data storage.
Mid-levelA complete design with a correct data model and API. Identifies the obvious bottlenecks and scales them with standard tools.
SeniorDrives the whole session. Goes deep on 1–2 hard parts, discusses failure modes, consistency and operations, and justifies every trade-off.
Staff+Handles ambiguity and scope, plans for evolution over time, considers cost and organizational impact, compares alternatives side by side.

How to spend 45 minutes

  1. 0–5 · Requirements. Functional: the 3–4 core features (and what's out of scope). Non-functional: users, read/write ratio, latency, availability vs consistency, durability.
  2. 5–10 · Estimates. QPS (average and peak), storage per year, bandwidth. Rough numbers are fine. Their purpose is to drive decisions ("100k writes/s, so one Postgres instance won't do").
  3. 10–15 · API and data model. 3–5 endpoints. The main entities, their keys, and which database fits the access pattern.
  4. 15–25 · High-level design. Draw the boxes: clients → LB → services → cache / DB / queue. Walk one request through it.
  5. 25–40 · Deep dives. The interviewer picks, or you propose, the hardest parts: hot keys, fan-out, consistency, a component failing, scaling 10×.
  6. 40–45 · Wrap up. Summarize the trade-offs, what you'd monitor, and what you'd change at 100× scale.

Fundamentals & failure

A distributed system is one where a computer you didn't know existed can make your own computer unusable. Designing for failure is the whole job.

Why distribute at all?

GoalTechniqueExample
ScalabilitySpread load over machines (partitioning, more stateless servers)Instagram's photo storage across thousands of nodes
AvailabilityRedundant copies so one failure isn't fatal (replication)A database replica takes over when the primary dies
Low latencyPut data near users (geo-replication, CDNs)Serving Europeans from Frankfurt, not Virginia
Organizational scaleSeparate services owned by separate teamsPayments team deploys without waiting for search team
First rule: don't distribute until you must. A single well-tuned PostgreSQL server handles thousands of transactions per second. Every network hop adds latency, failure modes and operational cost.

The eight fallacies of distributed computing

False assumptions engineers new to distributed systems make (L. Peter Deutsch and colleagues, Sun Microsystems):

  1. The network is reliable.
  2. Latency is zero.
  3. Bandwidth is infinite.
  4. The network is secure.
  5. Topology doesn't change.
  6. There is one administrator.
  7. Transport cost is zero.
  8. The network is homogeneous.

Failure models

ModelWhat can go wrongTypical handling
Crash-stopA node stops and never comes backReplication, failover
Crash-recoveryA node stops, then restarts (possibly losing memory)Durable logs, rejoin protocols
OmissionMessages are lostTimeouts, retries, acknowledgements
TimingMessages or processing are arbitrarily slow (GC pauses, overloaded network)Timeouts, leases, fencing tokens
ByzantineNodes lie or behave maliciouslyBFT protocols; mostly blockchains and aerospace

Most business systems assume crash-recovery nodes and an asynchronous network (no upper bound on delay). In that world you can never tell a slow node from a dead one. A timeout is a guess.

Timeouts, retries and idempotency

  • Timeouts: always set one. Too short causes false alarms and retry storms. Too long leaves users waiting. Base them on measured p99 latency.
  • Retries only for transient errors (timeouts, 503, connection reset). Use exponential backoff + jitter, a maximum number of attempts, and a retry budget so retries never exceed, say, 10% of traffic.
  • Idempotency: make operations safe to repeat. Natural (SET status = 'paid'), or with an idempotency key stored with the result. Then "at-least-once" delivery becomes "effectively once".
  • Deadlines propagate: if the user's request has 2s left, a downstream call shouldn't wait 5s. gRPC passes deadlines automatically.

Time, clocks & ordering

There is no global "now" in a distributed system. Each machine only knows its own clock and the messages it has received.

Physical clocks and their problems

  • Quartz clocks drift (roughly 10–100 ms per day). NTP syncs them over the network, typically to within a few ms on a LAN and tens of ms over the internet.
  • NTP can step a clock backwards. Never measure durations with wall-clock time. Use a monotonic clock (time.monotonic(), System.nanoTime()).
  • Last-write-wins by timestamp (Cassandra's default) can silently drop a write that really came later, if the writer's clock was behind.
  • Google Spanner uses GPS and atomic clocks (TrueTime), which give a bounded uncertainty interval. It waits out that uncertainty before committing, to get globally ordered transactions.

Happens-before

Event A happens before B (A → B) if they're on the same process and A came first, or A is sending a message and B is receiving it, or there's a chain of these. If neither A → B nor B → A, the events are concurrent: neither could have influenced the other.

Lamport clocks vs vector clocks

Lamport clockVector clock
StateOne counter per processOne counter per process in the system, in every process
RuleTick on each event; on receive: max + 1Tick your own entry; on receive: element-wise max, then tick your own entry
GuaranteeA → B implies L(A) < L(B)A → B if and only if V(A) < V(B)
Detects concurrency?NoYes: neither vector ≤ the other
Used forTotal ordering (break ties by process ID)Conflict detection in replicated data (Dynamo, Riak)
def merge(a, b):                    # vector clocks as dicts {process: counter}
    return {p: max(a.get(p, 0), b.get(p, 0)) for p in a.keys() | b.keys()}

def compare(a, b):
    le = all(a.get(p, 0) <= b.get(p, 0) for p in a.keys() | b.keys())
    ge = all(a.get(p, 0) >= b.get(p, 0) for p in a.keys() | b.keys())
    if le and not ge: return "a happened before b"
    if ge and not le: return "b happened before a"
    return "equal" if le else "concurrent: a conflict to resolve"

compare({"A": 2, "B": 1}, {"A": 1, "B": 2})    # concurrent

Hybrid logical clocks (HLC)

An HLC combines physical time with a logical counter, so timestamps stay close to wall-clock time while still respecting causality. CockroachDB and YugabyteDB use them.

Ordering guarantees you'll see in tools

  • Per-partition order (Kafka): messages with the same key stay ordered. There's no order across partitions.
  • FIFO queues (SQS FIFO): order per message group, with lower throughput.
  • Total order broadcast: everyone delivers every message in the same order. It's equivalent to consensus, and it's what Raft's log provides.

Replication in depth

Keeping copies is easy. Keeping copies in agreement while machines fail and networks lag is the hard part.

Three architectures

ModelWrites go toProsConsExamples
Single-leaderOne leaderSimple, no write conflictsLeader is a bottleneck; failover takes timePostgreSQL, MySQL, MongoDB, Redis, Kafka partitions
Multi-leaderAny of several leaders (often one per region)Local writes in every region; survives a region outageWrite conflicts must be resolvedCouchDB, multi-region MySQL setups, collaborative editors
LeaderlessSeveral replicas directly (quorum)No failover needed; highly availableWeaker consistency; read repair neededCassandra, ScyllaDB, DynamoDB, Riak

Quorums (leaderless)

With N replicas, a write waits for W acknowledgements, and a read queries R replicas and takes the newest version. If R + W > N, the read set and write set overlap in at least one replica, so the read sees the latest write. A common choice is N = 3, W = 2, R = 2.

Animation · quorum write and read with one replica down (N=3, W=2, R=2)

  • Read repair: when a read sees a stale replica, it writes the newest value back to it.
  • Anti-entropy: a background process compares replicas (using Merkle trees) and fixes differences.
  • Hinted handoff: if a replica is down, another node keeps its writes and hands them over when it returns.

Replication lag anomalies and fixes

AnomalyWhat the user seesGuarantee that fixes it
Stale own write"I saved my bio, but the page shows the old one"Read-your-writes: read from the leader, or wait until the replica reaches your write's position

Resolving write conflicts

  • Last write wins (LWW): keep the highest timestamp. Simple, but it silently loses data.
  • Keep all versions (siblings) and let the application or user merge them (Riak, Amazon's original shopping cart).
  • CRDTs (conflict-free replicated data types): counters, sets and text structures designed so any merge order gives the same result. Used by Redis Enterprise, Riak, Automerge and Yjs (collaborative editing).

Failover hazards

  • Async replication: the new leader may be missing the old leader's last writes. Those writes are lost.
  • Split brain: two nodes both believe they're the leader and both accept writes. Prevent it with consensus-based election and fencing tokens (see Consensus).
  • Tools that automate failover: Patroni (PostgreSQL + etcd), MySQL Group Replication / Orchestrator, MongoDB replica-set elections, Redis Sentinel.

Partitioning in depth

Partitioning is how one logical dataset grows past one machine. The partition key you choose decides which queries are cheap and which are painful.

Strategies

Choosing a partition key

  • It should have high cardinality (many distinct values) and spread traffic evenly.
  • Queries should usually include it. Otherwise each query must ask every partition (scatter-gather).
  • Hot keys (a celebrity's posts, a viral product) overload one partition. Fixes: add a random suffix to spread writes (post123#7) and merge on read, or cache the hot key.
  • Compound keys are common: Cassandra's PRIMARY KEY ((user_id), created_at) partitions by user and sorts by time within the partition.

Consistent hashing and virtual nodes

With plain hash % N, going from 4 to 5 nodes moves about 80% of keys. With a hash ring, it moves about 20%. Virtual nodes (each physical node appears at 100+ points on the ring) even out the load and spread a dead node's keys across all survivors. Redis Cluster uses a fixed set of 16,384 hash slots that are reassigned between nodes, which has the same effect.

  • Never rebalance with hash % N. Use a fixed number of partitions much larger than the node count, and move whole partitions (Kafka, Elasticsearch, Riak).
  • Routing options: any node forwards the request (Cassandra gossip), a routing tier (mongos, Vitess vtgate), or a partition-aware client (Kafka, Redis Cluster clients).
  • The cluster map usually lives in a coordination service: etcd, ZooKeeper, or the system's own Raft group.

Consensus & coordination

Consensus turns a group of unreliable machines into one reliable decision-maker. It's slow and precious, so systems use it for small, critical data: who's the leader, what's the config, who holds the lock.

Raft in detail

  • Roles: follower, candidate, leader. Time is divided into terms (1, 2, 3…), each with at most one leader.
  • Election: a follower that hears nothing for a random 150–300 ms becomes a candidate, increments the term, votes for itself and requests votes. Each node votes once per term, and only for a candidate whose log is at least as up to date as its own. A majority wins.
  • Log replication: clients send commands to the leader. The leader appends each one to its log and sends AppendEntries to followers. Once a majority has stored an entry, it's committed, applied to the state machine, and the client gets its answer.
  • Safety: committed entries are never lost, because any future leader must have received votes from a majority, and that majority overlaps with the majority that stored the entry.
Animation · Raft log replication and commit

Theory you should recognize

  • FLP impossibility: in a fully asynchronous network, no deterministic algorithm can guarantee consensus if even one node may crash. Real systems get around it with timeouts (partial synchrony) and randomness.
  • Paxos (Lamport): the original, proven, notoriously hard to understand. Multi-Paxos is used in Chubby and Spanner. Zab powers ZooKeeper. Raft was designed to be understandable: etcd, Consul, CockroachDB, TiKV, Kafka KRaft.
  • Throughput is limited by the leader and by a majority round trip per commit. Big systems run many Raft groups, one per partition (CockroachDB, TiKV).

Distributed locks, leases and fencing

A lock holder can pause (a GC pause, a VM migration) and wake up after its lease expired, still believing it holds the lock. The fix is a fencing token: an increasing number given out with each lock grant. The storage rejects writes carrying an older token.

# etcd lock with a lease (python-etcd3)
import etcd3
client = etcd3.client(host="etcd", port=2379)
with client.lock("invoice-run", ttl=30) as lock:   # lease expires if we die
    token = lock.revision                          # use as a fencing token
    storage.write(batch, fencing_token=token)      # storage rejects older tokens
Redis locks: a single-node SET key value NX PX 30000 is fine for efficiency (avoiding duplicate work), but not for correctness. Redlock across nodes is debated. For correctness, use etcd, ZooKeeper or Consul plus fencing.

Messaging & event streaming

Brokers decouple services in time (the receiver can be down) and in rate (the receiver can be slower). Most of the work is in delivery guarantees.

Three shapes

ShapeBehaviourTools
Work queueEach message goes to one of many workers, then is removedRabbitMQ, Amazon SQS, Celery (+Redis/RabbitMQ), Sidekiq
Pub/subEach message is copied to every subscriberAmazon SNS, Google Pub/Sub, Redis Pub/Sub, NATS
Log / streamRetained ordered log; each consumer group tracks its own offset; replayableApache Kafka, Redpanda, Amazon Kinesis, Apache Pulsar, Redis Streams

Delivery semantics

  • At-most-once: commit before processing. A crash loses the message. Fine for metrics sampling.
  • At-least-once: commit after processing. A crash causes a redelivery. This is the default, so consumers must be idempotent: deduplicate by message ID, or use upserts.
  • Exactly-once: Kafka transactions give exactly-once within Kafka (read → process → write to Kafka). Side effects elsewhere still need idempotency.

Kafka essentials

  • Topic → partitions (the unit of parallelism and ordering) → each partition replicated on several brokers (replication factor 3, min.insync.replicas=2, producer acks=all for durability).
  • Max useful consumers in a group = number of partitions. Choose partition counts with growth in mind.
  • Retention by time or size, or log compaction (keep only the latest value per key, which makes a topic usable as a changelog).
  • Ecosystem: Kafka Connect (move data in and out of databases and S3), Debezium (change data capture from database logs), Schema Registry (Avro/Protobuf schemas), Kafka Streams / ksqlDB / Flink (processing).
  • Consumer lag (newest offset − committed offset) is the key health metric.

Reliability patterns

  • Dead-letter queue (DLQ): after N failed attempts, park the message for inspection instead of blocking the queue forever.
  • Backpressure: when consumers fall behind, slow producers down or scale consumers up. Don't buffer without limit.
  • Transactional outbox + CDC: write the event into an outbox table in the same DB transaction, and let Debezium stream it to Kafka.

Event-driven architecture patterns

  • Event notification: "OrderPlaced {id}". Consumers fetch the details they need.
  • Event-carried state transfer: the event contains all the data, so consumers keep their own copy.
  • Event sourcing: store the sequence of events as the source of truth, and rebuild state by replaying them. You get an audit log for free, at the cost of complexity.
  • CQRS: separate write models from read models (for example, writes to PostgreSQL, events to Kafka, reads from Elasticsearch).

Distributed transactions

Atomic changes across machines are possible but expensive. Most microservice architectures choose eventual consistency with sagas instead.

Two-phase commit (2PC)

Animation · two-phase commit

  • Phase 1 prepare: each participant writes the change durably, locks it, and votes yes or no. Phase 2 commit/abort: the coordinator decides and tells everyone.
  • A participant that voted yes cannot change its mind. If the coordinator then disappears, the participant stays blocked, holding locks.
  • Where it's used: inside distributed databases (Spanner and CockroachDB run 2PC on top of Raft groups, so the coordinator itself is replicated), and XA transactions between a database and a message broker.

  • Avoid it entirely: often the best fix is redrawing service boundaries so data that must change atomically lives in one service.

Caching at scale

  • Cache stampede: a hot key expires and 1,000 requests hit the database at once. Fixes: per-key locks (single-flight), early randomized refresh, or serving stale data while one request refreshes it.

    count = r.incr(key)
    if count == 1:
        r.expire(key, window)
    return count <= limit

You can't fix what you can't see. In a distributed system, seeing means correlating metrics, logs and traces from dozens of services.

The pipeline

Metrics

Big data & stream processing

When the data is too big for one machine to process, send the computation to the data and run it in parallel on many machines.

MapReduce: the idea behind it all

Map each input piece to key-value pairs in parallel, shuffle so every value for a key lands on the same machine, then reduce each key's values to a result. Every stage is parallel and can be retried, so a dead machine just means rerunning its piece.

Streaming concepts

  • Event time vs processing time: events arrive late and out of order. Window by when they happened, and use watermarks to decide when a window is complete.
  • Windows: tumbling (fixed, non-overlapping), sliding, and session windows (grouped by bursts of activity).
  • State and checkpoints: Flink snapshots operator state, so after a crash it resumes exactly where it was.

Where the data lives

  • Data lake: raw files in object storage (S3) in columnar formats (Parquet), with table formats (Apache Iceberg, Delta Lake, Hudi) that add transactions and schema evolution.
  • Data warehouse: managed, SQL-first, columnar: Snowflake, BigQuery, Redshift, ClickHouse. Lakehouse (Databricks) merges the two.
  • Orchestration: Apache Airflow, Dagster and Prefect schedule pipelines as DAGs of tasks, with retries and backfills.
  • Lambda architecture runs batch and stream paths side by side. Kappa uses one streaming path, and reprocesses by replaying the Kafka log.

Case study: a chat system for 50 million users

Putting every topic together: how would you design WhatsApp-style messaging with the tools from this course?

Requirements

  • Functional: 1-to-1 and group chats (up to 500 members), online presence, delivery and read receipts, message history on every device.

Failure walkthrough

  • A gateway dies: clients reconnect (with jitter) to another one. Redis entries expire, and pending messages are redelivered from Kafka.

Concurrency coding

  • Senior coding rounds often add concurrency: a thread-safe cache, a bounded blocking queue, a rate limiter, a multi-threaded crawler, a delayed job scheduler.
  • Tools: a lock for mutual exclusion, and condition variables to wait for a state ("not full", "not empty") without busy-looping. Always wait in a while loop, because wake-ups can be spurious or stolen.

import threading
from collections import deque

class BoundedBlockingQueue:
    def __init__(self, capacity):
        self.q, self.cap = deque(), capacity
        self.lock = threading.Lock()
        self.not_full = threading.Condition(self.lock)
        self.not_empty = threading.Condition(self.lock)

    def put(self, item):
        with self.not_full:
            while len(self.q) == self.cap:     # while, not if: re-check after waking
                self.not_full.wait()
            self.q.append(item)
            self.not_empty.notify()            # wake one waiting consumer

    def take(self):
        with self.not_empty:
            while not self.q:
                self.not_empty.wait()
            item = self.q.popleft()
            self.not_full.notify()             # wake one waiting producer
            return item

Minutes 42–47

Senior object-oriented design

  • The senior bar for low-level design: clean interfaces, the right data structures for the complexity required, extensibility (new policies without rewrites), and thread safety.
  • The classic: an LRU cache with O(1) get and put, using a hash map plus a doubly linked list. Follow-ups: make it thread-safe, add TTLs, make the eviction policy pluggable (LRU/LFU), make it distributed.
  • State the invariants out loud ("the head is the most recent, every map entry points to a list node") and keep them true in every method.
Animation · LRU cache (capacity 3): hash map + doubly linked list

class Node:
    __slots__ = ("key", "val", "prev", "next")
    def __init__(self, key=0, val=0): self.key, self.val, self.prev, self.next = key, val, None, None

class LRUCache:
    def __init__(self, capacity):
        self.cap, self.map = capacity, {}
        self.head, self.tail = Node(), Node()          # sentinels: no empty-list edge cases
        self.head.next, self.tail.prev = self.tail, self.head
        self.lock = threading.Lock()                   # follow-up: thread safety

    def _unlink(self, n): n.prev.next, n.next.prev = n.next, n.prev
    def _push_front(self, n):
        n.prev, n.next = self.head, self.head.next
        self.head.next.prev = n
        self.head.next = n

    def get(self, key):
        with self.lock:
            n = self.map.get(key)
            if not n: return -1
            self._unlink(n); self._push_front(n)       # mark most recently used
            return n.val

    def put(self, key, val):
        with self.lock:
            if key in self.map: self._unlink(self.map[key])
            n = self.map[key] = Node(key, val)
            self._push_front(n)
            if len(self.map) > self.cap:
                lru = self.tail.prev                   # least recently used
                self._unlink(lru); del self.map[lru.key]

Worked design: a news feed

Twitter/Instagram-style home feed for 300M daily users. The core challenge is fan-out: delivering one post to millions of followers quickly without melting the write path.

Requirements

  • Functional: post (text and media), follow, view home feed (reverse-chronological or ranked), paginate.
  • Non-functional: feed loads in under 200 ms at p99, a post is visible to followers within seconds, high availability (eventual consistency is fine).

Estimates

reads : 300M users × 10 feed loads/day = 3B/day ≈ 35k QPS avg, ~150k peak
writes: 300M × 0.3 posts/day          = 90M/day ≈ 1k QPS avg
fan-out: average 200 followers → 90M × 200 = 18B feed inserts/day ≈ 200k/s
storage: posts 90M × 1 KB = 90 GB/day; feed caches hold IDs only (8 bytes each)

API and data

POST /v1/posts            {text, media_ids}            → {post_id}
GET  /v1/feed?cursor=...  → {posts: [...], next_cursor}
POST /v1/users/{id}/follow

posts      (post_id PK [Snowflake], author_id, text, media, created_at)  -- sharded by post_id
follows    (follower_id, followee_id)  -- two tables, one sharded each way
feed cache (Redis list per user: newest ~800 post_ids)

Architecture

Diagram · hybrid fan-out feed

Deep dive: push, pull, or hybrid

  • Push (fan-out on write): when you post, a worker appends the post ID to every follower's cached feed. Reads are O(1), but a celebrity with 50M followers creates 50M writes per post.
  • Pull (fan-out on read): at read time, fetch recent posts from everyone you follow and merge them. Writes are cheap, but reads are slow when you follow 2,000 accounts.
  • Hybrid (what's used in practice): push for normal authors. For authors above roughly 100k followers, don't push. At read time, merge their latest posts into the cached feed. Inactive users' feeds aren't precomputed at all; they're rebuilt on login.
  • Ranking: candidate generation (the merged IDs) → feature fetch → model score → re-rank. This is cached per user for a short time.

Failure modes and operations

  • Fan-out backlog (Kafka lag) delays posts. Alert on lag, autoscale workers, and give fan-out to active users priority.
  • Redis node lost: the feed rebuilds from the post store and follow graph (slower, but correct). Replicate the cache.
  • Deletes and privacy changes must propagate: filter at read time against a "deleted/blocked" set, because cached IDs can't be trusted alone.

Worked design: a payment system

Accept card payments for an e-commerce site through an external processor (Stripe or Adyen). The core challenge is correctness: never charge twice, never lose money, and always be able to explain every cent.

Requirements

  • Functional: create a payment for an order, charge through a payment service provider (PSP), handle refunds, record merchant balances.
  • Non-functional: exactly-once effect, full auditability, strong consistency for money, ~1k payments/s at peak, tolerant of PSP slowness and outages.

Data model: a double-entry ledger

payments (payment_id PK, order_id UNIQUE, amount_cents, currency, status, idempotency_key UNIQUE, psp_ref)
  status: CREATED → PENDING_PSP → SUCCEEDED | FAILED → (REFUNDED)

ledger_entries (entry_id, txn_id, account, debit_cents, credit_cents, created_at)   -- append-only
  every txn's debits = its credits, e.g. charge $50:
    debit  customer_receivable  5000
    credit merchant_payable      5000
  balances are SUMs over entries; never UPDATE a balance in place

Architecture

Diagram · payment flow with idempotency, outbox and reconciliation

Deep dive: never double-charge

  1. The client sends an Idempotency-Key. A unique constraint means a retry returns the stored result.
  2. The payment row is created as PENDING_PSP before calling the PSP, and the PSP call passes our payment_id as its idempotency key. Retrying the PSP call is then safe too.
  3. A PSP timeout means the result is unknown: leave it pending. The PSP webhook, or a status poll, settles it later. Never assume failure and charge again.
  4. On success, in one DB transaction: update the status, insert the ledger entries, and insert an outbox event, so "order paid" is published exactly when the money is recorded.
  5. A reconciliation job compares our ledger with the PSP's settlement report every day and flags any mismatch for review.

Failure modes

  • PSP down: queue the attempts with backoff, show "processing", and fail over to a second PSP for new payments if the business allows it.
  • Duplicate webhooks: handle them idempotently, applying a state transition only when moving forward.
  • Money-moving code changes: canary releases, plus reconciliation as a safety net.

Deep dives

  • Latency: one Redis round trip (~0.5 ms in the same zone). For very hot keys, use a local token cache: each gateway claims a batch of tokens from Redis and spends them locally.
  • Scale: a Redis Cluster sharded by limiter key. 2M ops/s needs roughly 20–40 shards.
  • Store down: decide per rule whether to fail open (allow traffic, which protects availability) or fail closed (block it, which protects security for logins). Fall back to local per-instance limits.
  • Rules live in a config store (etcd or a DB) and are pushed to gateways, so they change without a deploy.

Schema changes on big tables

  • Adding a nullable column is usually instant. Adding one with a default, changing a type, or adding an index can lock or rewrite the table.
  • Use online tools: gh-ost or pt-online-schema-change (MySQL), and CREATE INDEX CONCURRENTLY (PostgreSQL).
  • Renaming a column is a 5-step expand/contract (add new, dual-write, backfill, switch reads, drop old). Never just rename it in place.
  • Every migration must work with both the old and new versions of the app running, because deploys are rolling.

Breaking up a monolith (strangler fig)

  1. Put a routing layer (gateway or proxy) in front of the monolith.
  2. Pick a seam with clear data ownership and high value (for example, notifications). Build the new service.
  3. Route that path to the new service. The monolith calls the service through an interface instead of its own module.
  4. Move the data: the new service owns its tables, synced through CDC during the transition.
  5. Repeat, one seam at a time. Stop when the remaining monolith is healthy. Full decomposition is rarely the goal.

API evolution

  • Only make additive changes within a version (new optional fields and endpoints). Clients must ignore unknown fields.
  • Breaking change: a new version (/v2), run in parallel, with a deprecation timeline, usage metrics per client, and direct outreach to the biggest consumers.
  • In protobuf and Avro, never reuse field numbers, and keep schemas backward and forward compatible (enforce this with a schema registry).

Reliability, capacity planning & cost

Seniors are expected to talk about running a system, not just building it: how reliable it must be, how big it must get, and what it costs.

Reliability targets

  • RPO (recovery point objective): how much data you can lose. RTO (recovery time objective): how long you can be down. These drive the replication and backup design.
  • SLOs per critical user journey (checkout, login), with error budgets that set the pace of risky releases.
  • Failure domains: spread replicas across availability zones. Use multi-region only when the RTO/RPO or latency targets require it, because it multiplies cost and complexity.

Capacity planning in five steps

  1. Forecast peak load (growth trend × seasonality × launch events).
  2. Measure the capacity of one unit with a load test (for example, one pod handles 800 RPS at p99 under 200 ms).
  3. Units needed = peak ÷ per-unit capacity ÷ target utilization (around 60–70%), plus N+1 or N+2 redundancy.
  4. Check every downstream dependency: DB connections, cache memory, third-party quotas.
  5. Autoscale for daily cycles, and pre-scale for known events.

import threading, time

class TokenBucket:
    def __init__(self, rate, capacity):
        self.rate, self.cap = rate, capacity
        self.tokens, self.ts = capacity, time.monotonic()   # monotonic: never jumps back
        self.lock = threading.Lock()

    def allow(self) -> bool:
        with self.lock:
            now = time.monotonic()
            self.tokens = min(self.cap, self.tokens + (now - self.ts) * self.rate)
            self.ts = now
            if self.tokens >= 1:
                self.tokens -= 1
                return True
            return False

2 · Multithreaded web crawler

from concurrent.futures import ThreadPoolExecutor
from urllib.parse import urlparse

def crawl(start, fetch_links, workers=8):
    host = urlparse(start).netloc
    seen, lock = {start}, threading.Lock()
    with ThreadPoolExecutor(workers) as pool:
        pending = {pool.submit(fetch_links, start)}
        while pending:
            done = next(iter(pending)); pending.remove(done)
            for url in done.result():
                if urlparse(url).netloc != host: continue
                with lock:
                    if url in seen: continue
                    seen.add(url)
                pending.add(pool.submit(fetch_links, url))
    return seen

3 · Delayed task scheduler

import heapq, itertools

class Scheduler:
    def __init__(self):
        self.h, self.cv, self.seq = [], threading.Condition(), itertools.count()
        threading.Thread(target=self._run, daemon=True).start()

    def schedule(self, delay_s, fn):
        with self.cv:
            heapq.heappush(self.h, (time.monotonic() + delay_s, next(self.seq), fn))
            self.cv.notify()                     # an earlier task may now be first

    def _run(self):
        while True:
            with self.cv:
                while not self.h:
                    self.cv.wait()
                due, _, fn = self.h[0]
                wait = due - time.monotonic()
                if wait > 0:
                    self.cv.wait(timeout=wait)   # wake early if a sooner task arrives
                    continue
                heapq.heappop(self.h)
            fn()                                 # run outside the lock

4 · Read-write lock (many readers or one writer)

class RWLock:
    def __init__(self):
        self.cv, self.readers, self.writer, self.waiting_writers = threading.Condition(), 0, False, 0
    def acquire_read(self):
        with self.cv:
            while self.writer or self.waiting_writers:   # writer preference: no starvation
                self.cv.wait()
            self.readers += 1
    def release_read(self):
        with self.cv:
            self.readers -= 1
            if self.readers == 0: self.cv.notify_all()
    def acquire_write(self):
        with self.cv:
            self.waiting_writers += 1
            while self.writer or self.readers: self.cv.wait()
            self.waiting_writers -= 1; self.writer = True
    def release_write(self):
        with self.cv:
            self.writer = False; self.cv.notify_all()

What interviewers listen for

  • Always while, never if, around wait(). Never call user code while holding a lock. Lock ordering to avoid deadlock.
  • Granularity: one global lock (simple) vs lock striping (scales) vs lock-free structures.
  • Testing concurrency: stress tests with many threads, deliberate random sleeps, and invariant checks.

Code review checklist (in priority order)

  2. Read the error fully: stack trace bottom-up, logs around the timestamp.

Minutes 0–6

How an LLM generates text

  • Text is split into tokens (word pieces; about ¾ of a word each in English). The model sees token IDs, not letters, which is why it can stumble on spelling or character counts.
  • An LLM is a next-token predictor. Given the tokens so far, it outputs a probability for every token in its vocabulary. One token is sampled, appended, and the loop repeats.
  • Temperature reshapes those probabilities: low means near-deterministic (extraction, code), high means more varied (brainstorming). Top-p samples only from the smallest set of tokens that covers p of the probability.
  • The context window is the maximum tokens in and out per call. Everything the model "knows" about your task must fit in it. It has no memory between calls.
  • Training: pretraining on huge text corpora, then instruction tuning (SFT) and preference tuning (RLHF or DPO) to make it a helpful assistant.
Animation · generating one token at a time 

import numpy as np
def sample(logits, temperature=1.0, top_p=1.0):
    z = logits / max(temperature, 1e-6)           # low T sharpens, high T flattens
    p = np.exp(z - z.max()); p /= p.sum()         # softmax → probabilities
    order = np.argsort(-p)
    keep = order[np.cumsum(p[order]) - p[order] < top_p]   # nucleus (top-p)
    q = p[keep] / p[keep].sum()
    return np.random.choice(keep, p=q)            # next token id

Minutes 6–10

Attention & the transformer

  • Each token becomes a vector (an embedding). Self-attention lets every token look at every earlier token and mix in information from the relevant ones.
  • Each token makes a query; every token offers a key and a value. Weights = softmax(Q·K / √d). The output is the weighted sum of the values.
  • Many heads run in parallel (one tracks grammar, another references…), and dozens of layers stack. A decoder-only transformer with a causal mask is the architecture behind GPT, Claude, Llama and Gemini.
  • Cost grows with the square of the sequence length, so long prompts are slower and more expensive. The KV cache stores past keys and values so each new token doesn't recompute them.
Animation · what "it" pays attention to

def attention(Q, K, V, causal=True):
    d = Q.shape[-1]
    scores = Q @ K.T / np.sqrt(d)                       # similarity of each query to each key
    if causal:
        scores += np.triu(np.full(scores.shape, -1e9), 1)   # can't look at future tokens
    w = np.exp(scores - scores.max(-1, keepdims=True))
    w /= w.sum(-1, keepdims=True)                       # softmax per row
    return w @ V                                        # weighted mix of values

Minutes 15–21

Embeddings & vector search

  • An embedding model turns text into a vector (often 384–3,072 numbers), so that texts with similar meaning land close together, even with no shared words.
  • Similarity is usually cosine similarity (the angle between vectors). Search means embedding the query and finding the nearest stored vectors.
  • Exact search is O(n) per query. At millions of vectors, use approximate nearest neighbour (ANN) indexes such as HNSW (a graph) or IVF/PQ (clusters plus compression): about 95–99% recall in milliseconds.
  • Stores: pgvector (Postgres), Pinecone, Weaviate, Qdrant, Milvus, OpenSearch/Elasticsearch, FAISS (a library).
  • Keyword search (BM25) still wins on exact terms (error codes, names). Production systems often use hybrid search that combines both.

Minutes 21–28

Retrieval-augmented generation (RAG)

  • RAG grounds answers in your data: retrieve relevant passages, put them in the prompt, and ask the model to answer from them, with citations.
  • Offline: load documents → clean → chunk (for example, 300–800 tokens with overlap, split on headings) → embed → index, with metadata such as source, date and permissions.
  • Online: (optionally rewrite the query) → hybrid retrieve the top ~20–50 → rerank to the top ~5 with a cross-encoder → build the prompt → generate with citations → check grounding.
  • Most RAG failures are retrieval failures. Measure retrieval separately (recall@k) from generation (faithfulness, answer quality).
  • Choose RAG when knowledge changes or is private. It's cheaper and more updatable than fine-tuning, and it gives citations.

Minutes 28–34

Agents & tool calling

  • An agent is an LLM in a loop: decide the next action → call a tool → read the result → repeat until done. The model chooses the path, and your code executes each step.
  • Prefer the simplest thing that works: a single call, then a fixed workflow (chain, router, parallel steps), then a full agent, only when the steps can't be known in advance.
  • Design tools like APIs for a new colleague: clear names, focused purposes, typed parameters, helpful error messages, and results that aren't enormous.
  • Guardrails: step and token budgets, timeouts, read-only tools by default, human confirmation for irreversible actions, sandboxing, and full traces for debugging.
  • MCP (Model Context Protocol) is a standard way to expose tools and data sources to many AI applications.

def run_agent(goal, tools, llm, max_steps=8):
    messages = [{"role": "user", "content": goal}]
    for step in range(max_steps):                       # hard budget: no infinite loops
        reply = llm.chat(messages, tools=[t.schema for t in tools.values()])
        messages.append(reply.message)
        if not reply.tool_calls:
            return reply.text                           # model decided it's done

            tool = tools[call.name]
            if tool.dangerous and not confirm_with_user(call):
                result = "User declined this action."
            else:
                try: result = tool.run(**call.args)
                except Exception as e: result = f"Tool error: {e}"   # let the model recover

Minutes 40–45

Prompting vs RAG vs fine-tuning

  • Prompting first: it's the cheapest and fastest to iterate. Many "we need fine-tuning" problems are really prompt or eval problems.
  • RAG adds knowledge: private, changing, citable facts.
  • Fine-tuning changes behaviour: a consistent format or style, a narrow task done cheaply by a smaller model, or lower latency and cost at high volume. It doesn't reliably add new facts.
  • LoRA / QLoRA train small adapter matrices instead of all the weights: far cheaper, and easy to swap. Distillation trains a small model on a large model's outputs.
  • You need high-quality training examples (hundreds to thousands), a held-out eval set, and a check for regressions on general ability.

Minutes 45–51

Latency, throughput & cost

  • Latency has two parts: time to first token (TTFT: grows with prompt length and queueing) and time per output token. Output tokens are much slower than input tokens, so stream responses to the user.
  • Cost is priced per million input and output tokens, with output costing more. Long system prompts and RAG context add up quickly, so estimate them.
  • Levers: shorter prompts, prompt caching (reuse a long static prefix at a discount), response caching, model routing (a small model for easy requests, a large one for hard), batch APIs for offline work, and max output limits.
  • Self-hosting: GPU memory ≈ parameters × bytes per parameter (70B at 16-bit ≈ 140 GB, plus KV cache). Servers like vLLM use continuous batching and paged KV cache. Quantization (8- or 4-bit) trades a little quality for memory and speed.

Minutes 51–56

Safety & prompt injection

  • Prompt injection: text in the input (a web page, an email, a PDF, a tool result) contains instructions the model follows instead of yours. It's the #1 security issue for LLM apps, and especially dangerous with tools.
  • No prompt fully prevents it, so design for it: treat all retrieved and tool content as untrusted data, use least-privilege tools, require human confirmation for sensitive actions, never put secrets in prompts, and don't auto-render model-generated links or images that can leak data.
  • Also: jailbreaks (users bypassing your rules), PII leakage (redact it before logging, respect retention), hallucination (grounding plus citations plus "I don't know"), and harmful content (moderation).
  • Validate outputs in code: schemas, allow-lists for actions, and limits on amounts and recipients.

Transformers & LLM training in depth

You won't be asked to derive back-propagation, but you will be asked to explain what happens inside the model at the level of tokens, attention, layers and training stages.

The pipeline inside one forward pass

  1. Tokenize: byte-pair encoding (BPE) splits text into subword pieces from a fixed vocabulary (~50k–200k tokens).
  2. Embed: each token ID becomes a learned vector. Position information is added (today usually rotary embeddings, RoPE).
  3. Transformer blocks ×N: each block is multi-head self-attention, then a feed-forward network (MLP), with residual connections and layer normalization.
  4. Output: the final vector of the last position is projected to vocabulary logits, then sampled.

Training stages

StageDataResult
PretrainingTrillions of tokens of web, books and code; predict the next tokenA base model: knows a lot, but isn't a good assistant
Supervised fine-tuning (SFT)Curated instruction → response pairsFollows instructions and formats
Preference tuning (RLHF, DPO, constitutional/RLAIF)Comparisons of better vs worse responsesMore helpful, honest and harmless
Reasoning trainingReinforcement learning on verifiable tasks (maths, code)Models that "think" step by step before answering

Why LLMs hallucinate

  • The model is trained to produce plausible continuations, not to look things up. When it lacks the knowledge, a fluent guess often scores better than "I don't know".
  • Mitigations: grounding with retrieval, instructions to abstain, citations checked against sources, lower temperature for factual tasks, and verification steps or tools.

Key numbers

  • Attention cost is O(n²) in sequence length, and memory for the KV cache is O(n × layers × hidden size), so long contexts cost real money and latency.
  • Parameter memory: 7B at fp16 ≈ 14 GB, 70B ≈ 140 GB. At 4-bit, 70B ≈ 35–40 GB.
  • Mixture-of-experts models activate only some parameters per token: lots of knowledge capacity at lower compute per token.

RAG & retrieval in depth

Retrieval quality caps answer quality. Most RAG improvements come from better chunking, hybrid search, reranking and evaluation, not from a bigger model.

Chunking

  • Split on structure (headings, sections, functions in code) before falling back to fixed sizes. Use 10–20% overlap so ideas aren't cut in half.
  • Too small, and chunks lack context. Too big, and similarity gets diluted and tokens are wasted. Tune the size with retrieval evals.
  • Contextual chunks: prepend a short summary of where the chunk sits ("From the 2025 refund policy, section 3…") before embedding. This improves retrieval noticeably.
  • Store metadata (source, date, author, permissions) for filtering and citations.

Retrieval

TechniqueWhy
Hybrid: BM25 + vectors, merged with reciprocal rank fusionKeywords catch exact terms; vectors catch paraphrases
Reranking with a cross-encoderScores query and passage together, which is much more accurate than embedding distance. Apply to the top 20–50 only
Query rewriting / expansionResolves follow-ups ("what about it?") and adds synonyms
Metadata filtersPermissions, recency, product version
Multi-hop / agentic retrievalQuestions that need several lookups
def rrf(rankings, k=60):                     # reciprocal rank fusion
    score = {}
    for ranking in rankings:                 # e.g. [bm25_ids, vector_ids]
        for rank, doc_id in enumerate(ranking):
            score[doc_id] = score.get(doc_id, 0) + 1 / (k + rank + 1)
    return sorted(score, key=score.get, reverse=True)

Evaluating RAG

RetrievalRecall@k, MRRA labelled set of question → relevant chunk IDs

Debugging wrong answers

  1. Was the right chunk in the corpus at all? If not, it's ingestion.
  2. Was it retrieved in the top k? If not, look at chunking, embeddings, hybrid search, or the query.
  3. Was it ranked into the prompt? If not, look at reranking and the context budget.
  4. Did the model use it correctly? If not, look at the prompt, conflicting chunks, or the model choice.

Tool design checklist

  • A few well-named tools that each do one clear job, rather than dozens of overlapping ones.

Evals in depth

Teams that ship reliable AI products are the ones with good evals. In interviews, a thoughtful eval plan is often the deciding signal.

Building the golden set

  1. Collect real inputs (logs, support tickets), not ones you invented.
  2. Cover slices: common cases, hard cases, edge cases, adversarial inputs, each language, each customer tier.
  3. Write the expected outcome or a rubric. Have two people label a sample and check that they agree.
  4. Start with 50–100 cases, then grow it with every production failure.

Graders

GraderStrengthWeakness
Code assertionsFast, cheap, deterministicOnly for objective checks
Reference comparisonGood for extraction and classificationOpen-ended text has many right answers
LLM-as-judgeScales to subjective qualitiesBiases (verbosity, position, self-preference). Calibrate against humans and use binary, specific criteria
Pairwise preferenceMore reliable than absolute scoresOnly tells you which is better
Human reviewThe ground truthSlow and expensive. Use for calibration and spot checks

Process

  • Look at actual outputs first (error analysis), group the failures into categories, and only then write graders for those failure modes.
  • Run evals in CI on every prompt, model or retrieval change. Track results per slice and block releases on regressions.
  • Online: log everything with trace IDs, sample real traffic for review, and A/B test significant changes.

Fine-tuning is a powerful but slow-moving tool. Reach for it after prompting and RAG plateau on a measured eval.

MethodWhat changesCostUse for
Full fine-tuningAll weightsVery highRarely, for big domain shifts with lots of data

Doing it right

  • Data quality beats quantity: hundreds of excellent examples beat thousands of noisy ones. Deduplicate, and balance the classes.
  • Hold out an eval set from the same distribution, and also test general ability for catastrophic forgetting.
  • Compare against a strong prompted baseline on the same eval. Fine-tuning has to beat that, not a weak prompt.
  • Plan for retraining when the base model or the data changes, and version the datasets and adapters.

Inference, latency & cost in depth

LLM calls are often the slowest and most expensive part of a request. Knowing the levers is a strong senior AI signal.

Latency anatomy

PartDriven byLevers
QueueingLoad and rate limitsCapacity, priority tiers, fallbacks
Prefill / TTFTInput length, model sizeShorter prompts, prompt caching, smaller models
DecodeOutput tokens × time per tokenCap output length, concise formats, speculative decoding, smaller models
Your pipelineRetrieval, tools, retriesParallelize, cache, set timeouts

Cost levers, biggest first

  1. Model routing: a small, cheap model handles most requests, and hard ones escalate (with a classifier or a confidence check).
  2. Prompt caching of the long, static prefix (system prompt, tools, documents).
  3. Trim context: fewer, better chunks after reranking, and summarized conversation history.
  4. Response caching for repeated questions: exact-match first, semantic caching carefully.
  5. Batch APIs for offline jobs (often about half price), and output length limits.

Self-hosting basics

  • Throughput comes from continuous batching (new requests join the batch as others finish) and paged KV cache (vLLM, TGI, SGLang, TensorRT-LLM).
  • Quantization (int8, int4, FP8) cuts memory and raises speed for a small quality loss, so measure it on your evals.
  • Speculative decoding: a small draft model proposes tokens, and the large model verifies several at once.
  • Self-hosting only beats APIs at sustained high utilization, or when you need privacy or customization. Include the cost of GPUs and the people to run them.

AI safety & security in depth

The model can't reliably tell your instructions apart from instructions hidden in its inputs. Security comes from the system design around the model.

The "lethal trifecta" rule of thumb

An agent with access to private data, exposure to untrusted content and a way to communicate externally can be tricked into leaking that data. Remove at least one of the three for any workflow that handles sensitive data.

Case study: an AI customer-support assistant

"Design an AI assistant that answers customer questions from our help center and can process simple refunds." This is the most common LLM system design question.

Requirements and numbers

  • Answers grounded in about 5,000 help-center articles, with citations. It can look up orders and issue refunds up to $50 with user confirmation, and escalates to a human otherwise.
  • 200k conversations a month, about 4 turns each. Target: first token in under 1.5 s, at least 60% resolved without a human, no harmful or unauthorized actions.
  • Rough tokens per turn: 2k system + tools (cached), 2k retrieved context, 500 history, 300 output → estimate cost with the calculator in the crash course.

Architecture

Diagram · support assistant

Key decisions

  • Retrieval: hybrid search over the chunked articles, with contextual chunk headers, plus a reranker, filtered by product and locale.
  • Tools: lookup_order (read-only, scoped to the authenticated customer) and issue_refund (the amount is validated in code against order and policy, and the customer must confirm in the UI).

Deep dive

Delivery & presence

The same story lands differently depending on how it's told. These are small habits with a big effect.

  • Signpost: "Two minutes of context, then what I did, then results." Interviewers relax when they can see the structure.
  • Pace: about 150 words per minute. Pause after the result. Silence is fine, so let them ask.
  • Check in: "Would you like more detail on the technical side or the people side?" It shows awareness and lets them steer to their rubric.
  • Notes: a one-line cue per story (title + 3 numbers) is fine in video interviews. Don't read paragraphs.
  • Video setup: camera at eye level, good light, headphones, closed notifications, water nearby.
  • Nerves: rehearse each story out loud 3+ times. Familiarity is the best cure for nerves.
  • Honesty about memory: "I don't remember the exact number, but it was roughly 40%" is better than a made-up figure.
